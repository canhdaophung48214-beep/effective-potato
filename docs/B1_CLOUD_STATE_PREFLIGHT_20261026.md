## 4. 由快照推出的三条事实

1. **`batchId = "seed-s01-20261022"`**：现存的 1+3+4 条是 **S2 演示批次**，创建于 2026-10-22 12:22:31；**pilot 批次 `pilot_c02_batch1_20261022` 从未写入过云端**。
2. **命名仍是旧形态**：`d01`、`s01_t2`、`s01_f1`。这解释了 C2-A 的 F-1：`submit` 的形状校验（`^c\d{2}$` 等）会先拒掉这些 ID，`TARGET_IS_DEMO` 在云端不可达。
3. **`dishes` 对客户端可读**：一旦写入 12 条 `field_unverified` 记录，任何登录态用户都能直接查询到它们（小程序界面不展示，但数据可被读）。这是写入前必须知情的事实。

## 7. 下一步：两种部署方案（均需单独授权）

线上版本落后一天，本地的六项复核根本没上去过。因此「先预演」这条路不存在——得先把新版本放上去。两条路：

### 方案 A：覆盖部署 `seed`

- 操作：开发者工具中右键 `cloudfunctions/seed` → 上传并部署（云端安装依赖）。
- 优点：一步到位，函数名不变，后续 `plan`/`write`/`rollback` 直接可用。
- 代价：**旧代码不可恢复**（无版本、无备份、未入 Git）。一旦新版本有运行时错误，只能靠本地排查后再次部署，无法退回 10-22 那版。

### 方案 B：并行部署 `seed_b1`（推荐）

- 操作：新增 `cloudfunctions/seed_b1/`（内容为当前 `seed` 的副本），单独部署；老 `seed` 原样不动。
- 优点：**零风险**——旧函数不受影响，随时可弃；先在 `seed_b1` 上跑 `plan`（只读）验证批次识别、六项复核、`rollbackPlan` 是否按预期工作。
- 代价：多一个函数目录、多一次部署；验证通过后仍需把 `seed` 也更新一次（否则线上权威函数仍是旧版）。
- 前提：新增目录属项目文件变更，需你授权。
