## 一、官方证据（逐条）

### 1.1 个人主体服务类目 [官方原文]

来源：`https://developers.weixin.qq.com/miniprogram/product/material/`（小程序类目）

- 个人主体「工具」类目包含：记账、日历、天气、办公、图片处理、计算器、报价/比价、**信息查询**、预约/报名、健康管理、备忘录。
- **「工具-信息查询」资质要求栏为空**，适用范围原文：「适用于提供信息查询功能。」
- 同类目内对 UGC 的排除（原文要点）：
  - 备忘录：「**不涉及用户原创内容的传播及公开访问**。」
  - 记账：排除「提供用户自定义生成内容记录及分享」。
- **个人主体类目列表中不存在「社区/论坛」「笔记」等 UGC 类目**；此类类目只出现在非个人主体列表。

**推论（有限定）**：当前类目允许「信息查询」，但**明确不包含用户原创内容的传播与公开访问**。因此「用户投稿 → 审核 → 公开展示」在个人主体 + 工具-信息查询 组合下**缺乏类目依据**。

## 二、当前限制（结论）

1. **类目层面**：个人主体「工具-信息查询」允许查询功能，**排除用户原创内容的传播与公开访问**。→ 「公开展示用户投稿」在当前主体+类目下**没有依据**。
2. **规范层面**：只要存在 UGC（即使是内部审核），5.18/10.2/10.4 即要求内容安全检测与人工审核；3.10/10.3 要求投诉举报通道；15.1 要求隐私告知。
3. **接口层面**：接口名称/路径已确认；**可用性与开通条件未核实**，须后台实测。
4. **项目现状**：账号为个人主体；当前无任何 UGC 功能（评分/社区已按合规改版为本地筛选）。

## 三、两条可行路径

### 路径 A：保留当前类目，只做「非公开纠错建议」

| 项 | 内容 |
|---|---|
| 允许做什么 | 用户提交**纠错/补充信息**（菜名、价格、档口），内容**仅运营者可见**，**不向任何其他用户展示**；运营者据此修订**自有数据**（`data/dishes.js` 等），对外展示的始终是运营者撰写的内容 |
| 依据 | 「信息查询」允许查询功能；不构成「用户原创内容的传播及公开访问」；对外文案由运营者改写，非用户原文 |
| 必要条件 | ① 内容安全接口可用且实际接入（5.18/10.2）；② 隐私告知与同意（15.1）；③ 投诉举报入口（3.10/10.3）；④ 后台类目保持「工具-信息查询」 |
| 风险 | **中**：审核人员可能将「用户提交 + 数据由用户内容驱动更新」判定为变相 UGC；需在提审说明与隐私指引中明确「投稿不公开展示、仅作纠错参考」 |
| 成本 | 低：2 个集合 + 2–3 个云函数 + 1 个隐藏审核页；无主体变更 |
| 能支撑的 MVP | 纠错闭环（用户报错 → 运营者核实修订），**不能**支撑「用户共建菜单/公开展示投稿」 |

### 路径 B：变更主体/类目以获得公开 UGC 资格

| 项 | 内容 |
|---|---|
| 允许做什么 | 用户投稿审核通过后**公开展示**（真正的 UGC 共建） |
| 必需条件 | ① **主体变更**：个人 → 企业/个体工商户（个人主体类目表无社区/论坛/笔记等 UGC 类目）；② 类目申请（如「生活服务-餐饮」或「社区/论坛」，以后台实际可选项为准）及对应资质（餐饮类可能需食品经营相关资质，**具体以类目页为准，本轮未核实**）；③ 内容安全接口全部接入（文本+图片异步）；④ 人工审核流程 + 巡查机制（10.5）；⑤ 侵权投诉机制（3.10）；⑥ 隐私政策与用户协议更新；⑦ 可能需补充「用户发布内容」相关审核材料 |
| 风险 | **低（合规）**，但**成本高、周期长**：主体变更涉及认证/年审，类目资质审核时间不可控 |
| 成本 | 高：主体与资质办理 + 全部 UGC 合规设施 |
| 能支撑的 MVP | 完整用户共建（投稿公开、审核、展示） |

### 差异速览

| 维度 | A（保留类目） | B（变更主体/类目） |
|---|---|---|
| 投稿是否公开 | **否**（仅运营者可见） | 是（审核通过后公开） |
| 主体/类目变更 | 不需要 | **必需** |
| 内容安全接口 | 必需（若判定为 UGC） | 必需（强制） |
| 投诉举报入口 | 必需 | 必需 |
| 研发量 | 小（submissions/upload_logs + 审核页） | 中（同上 + 公开展示与举报处理闭环） |
| 上线周期 | 1–2 周（若接口权限可开） | 数周–数月（取决于资质） |
| 主要风险 | 被判定变相 UGC | 资质/时间成本 |

## 四、推荐的最小实现顺序

1. **先核实接口权限（1 天，零代码）**：负责人登录 mp 后台 →「开发管理-接口设置」查看「内容安全」是否可开通、个人主体是否受限，截图留档。若不可开通 → 路径 A 也不成立，须先解决权限或改主体。
2. **选定路径**：若只做纠错 → A；若必须公开投稿 → B（先办主体）。
3. **路径 A 最小研发（按序）**：
   a. 云函数 `submit`：服务端校验字段（复用 D5 价格规则）+ 调文本/图片安全检查（若可用）+ 写 `submissions{pending}` + `upload_logs`；
   b. 云函数 `review`：管理员 openid 白名单，`pending → approved/rejected`，全量写日志；
   c. 隐藏页 `pages/review/`（非 tabBar，入口不公开）；
   d. 隐私指引更新（收集内容/图片、用途、保留期）+ 投诉入口（客服消息或固定页面）；
   e. **交付运营者修订**：approved 内容仅供运营者参考，**不进入公开数据集**；运营者人工改写后按既有流程更新 `data/dishes.js`。
4. **ID 策略（固定，不得变更）**：投稿及其审核结果**永不进入** `id-map.json`、**不得**自动获得 dishId、`verifyStatus` 保持 `unverified`、`import_eligibility` 恒 `blocked`；若未来某条投稿被采纳为正式菜品，须走**独立规划 + 新审批**，与首批 104 条冻结映射彻底隔离。
5. **路径 B 最小研发**：在第 3 步之上增加「公开查询只读 approved（且已完成安全检测）」「举报入口 + 处理工单」「巡查记录」。

### 数据模型（两路径共用，仅 B 加公开读）

- 集合 `submissions`：`kind / payload / photos(fileID[]) / submitter(openid，仅服务端) / status(pending|approved|rejected) / review{by,at,reason,edits} / dedupe{key,dupOf} / createdAt / updatedAt`。
- 集合 `upload_logs`：`{action, submissionId, by, at, before, after}`，只追加。
- 权限：客户端仅可创建与读自己的投稿；`status` **只能由云函数写**；公开查询（仅 B）走云函数，永不直接读集合。
