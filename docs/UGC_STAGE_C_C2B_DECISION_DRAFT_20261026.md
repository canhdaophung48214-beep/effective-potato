## 0 这份草案要回答什么

C2-A 有一个用例（A4：demo 目标拒绝）**在云端不可达**，原因是云端 4 条菜品文档的 `_id` 是 `d01` 这类早期命名，不满足 `submit` 的 ID 契约。要让它可达，只有两条路：

- **方案 A**：不写数据，接受该分支"云端未验证"。
- **方案 B**：写入一条专用临时测试菜品，让请求能走到 `TARGET_IS_DEMO`。

本文把两条路的代价、风险、回滚和"证据能代表什么"摊开，供你决定。

## 2 方案 A：继续等待合规数据

**做什么**：不写任何测试菜品。A4、成功投稿、内容安全、审核变更路径全部保留为"未验证"。

**优点**
- 零业务数据污染：`dishes` 永远只有真实的 4 条 demo。
- 无删除环节：不存在"测完忘了删"的遗留风险。
- 不触碰"不创建测试菜品"红线，后续任何审计都干净。

**缺点**
- A4 的云端行为永远缺少证据，只能靠本地模拟 + 源码静态检查支撑。
- 成功路径（入库/去重/限流/内容安全/审核动作）同样继续无法验证——因为缺的不止是 A4 的 demo 文档，还缺一条 `field_unverified` 目标。

**什么时候自然解套**：正式菜品数据（B1 数据导入）落地后，云端自然出现合规 `_id` 与 `field_unverified` 文档；那时 A4 与成功路径一起可测，且测的是**真实数据**，证据价值高于人造测试数据。

**需要负责人做什么**：无。维持现状即可。

## 3 方案 B：专用临时测试菜品

**做什么**：在 `dishes` 写入一条专用文档，让 A4 可达；测完删除。

### 3.1 必须拆成两步，不能一步到位

| 步骤 | 目标 | 文档 | 能验证什么 |
|---|---|---|---|
| **B1** | 触达 `TARGET_IS_DEMO` | `_id:"c99_d001"`、`dataClass:"demo"` | 只验证"demo 被拒"这一条 422 分支 |
| **B2** | 走通成功投稿 | 另建 `_id:"c99_d002"`、`dataClass:"field_unverified"` | 入库、去重、限流、内容安全、审核动作 |

**关键**：B1 的文档**不能**顺手改成可投稿状态。`demo` 与 `field_unverified` 是两种语义，改一个字段就变成"把演示数据伪装成可核验数据"，这正是设计明令禁止的（`TARGET_NOT_VERIFIABLE` 分支就是为它准备的）。B2 必须另建文档，且意味着**允许产生测试投稿记录**——这与 C2-A 指令"不创建测试投稿"直接冲突，需要单独一句话解除。

### 3.2 B1 候选文档（字段照抄既有 demo 结构，避免引入新字段）

| 字段 | 建议值 | 说明 |
|---|---|---|
| `_id` | `c99_d001` | 满足 `^c\d{2}_d\d{3}$` |
| `dataClass` | `demo` | 触达 `TARGET_IS_DEMO` 的关键字段 |
| `name` | `__C2_TEST__ 临时测试，请勿引用` | 一眼可辨，防误用 |
| `restaurantId` | `c99` | 与 `_id` 命名空间一致 |
| `stallId` | `c99_t01` | 满足 `^c\d{2}_t\d{2}$` |
| `price` | `9.9` | 数字类型 |
| 其他字段 | 照抄一条现有 demo 文档 | 不新增字段、不改结构 |

**注意**：`dishes` 是"所有用户可读"集合，这条文档写入后**任何客户端都能查到**（包括 `__C2_TEST__` 这个名字）。小程序页面不读云端 `dishes`（`pages/index/index.js:9` 用本地数据），所以不会显示在界面上；但"能被查出来"这一点必须记录，不能声称"对用户不可见"。

### 3.3 插入前快照（必须做，且留证）

1. 控制台 `dishes` 集合：记录**条数**（应为 4）、**四条 `_id` 全列表**、**权限原文**（"所有用户可读"）；
2. 截图一张（集合列表 + 条数）；
3. 记录 `submissions`（0）与 `upload_logs`（1）当前条数，作为测试后对比基线。

**判据**：快照四要素齐全才允许插入；缺任何一项 → 停，不插。

### 3.4 插入步骤（负责人执行，DS 只给内容）

1. 控制台 → 数据库 → `dishes` → **添加记录**；
2. 按 §3.2 字段逐项填写（不要用"导入 JSON"以免结构漂移）；
3. 提交前自查：`_id` 是否 `c99_d001`、`dataClass` 是否 `demo`、`name` 是否带 `__C2_TEST__`；
4. 保存，记录**插入时间**。

### 3.5 插入后核对（三项，任一不符即停）

| 核对项 | 期望 |
|---|---|
| 集合条数 | 4 → **5** |
| 新文档字段 | `_id`、`dataClass`、`restaurantId`、`stallId` 与 §3.2 一致 |
| 其余四条 | `_id` 列表与快照完全一致（未被改动） |

### 3.6 C2-A4 复测（唯一允许的调用）

用 A4 原脚本（`shopId:'c99'`、`stallId:'c99_t01'`、`dishId:'c99_d001'`），只改这三个值：

- 期望：`{ok:false, code:"TARGET_IS_DEMO", httpStatus:422}`；
- 同时核对：`submissions` 仍 0 条、`upload_logs` 条数不变（该分支不写日志，`cloudfunctions/submit/index.js:516`）；
- 若返回 `TARGET_NOT_FOUND` → 说明文档没写进去或环境不对，**停**；
- 若返回 200/入库 → 说明 `dataClass` 没写对，**停**，不要重试。

### 3.7 删除（**必须是独立授权步骤**）

1. 单独确认"授权删除 `c99_d001`"；
2. 控制台删除该文档；
3. 核对：条数回到 **4**、`_id` 列表与快照**逐条一致**、`__C2_TEST__` 查不到；
4. 若删除失败或条数回不到 4 → **停止后续所有测试**，报告实际条数与残留 `_id`，**不得自行清理其他数据**（不删别的文档、不改权限、不重置集合）。

### 3.8 异常停止条件（命中任一即停，不自行补救）

1. 插入后条数不是 5；
2. 其余四条 demo 文档被改动（`_id`/`dataClass` 变化）；
3. A4 返回的不是 `TARGET_IS_DEMO`；
4. `submissions` 出现任何新记录；
5. `upload_logs` 条数非预期增加；
6. 删除失败、或删回到不了 4 条；
7. 控制台出现权限/索引/环境变量被改动的提示；
8. 任何"先清理一下再继续"的冲动——一律停，报告。

### 3.9 风险清单

| 风险 | 严重度 | 说明 |
|---|---|---|
| 污染真实集合 | 中 | `dishes` 是业务集合，插入即进入真实数据面 |
| 忘记删除 | 中 | 需人工核对；删除本身要二次授权，增加一次操作窗口 |
| 被误当真实菜品 | 低 | `name` 带 `__C2_TEST__`；页面不读云端 `dishes` |
| 客户端可查得 | 低 | 集合所有用户可读，但页面不展示 |
| 命名空间被误留 | 中 | `c99` 不在真实批次（c02）内，但仍应删净 |
| 证据价值有限 | 低 | 验证的是"我们造的 demo 文档被拒"，不是"真实 demo 数据被拒" |

| 维度 | 方案 A（等待合规数据） | 方案 B1（只插 demo 文档） | 方案 B2（再插 field_unverified） |

## 5 推荐

**推荐方案 A**，理由：C2-A 的核心价值（鉴权、校验、保留字段、审计脱敏、空队列、直读拒绝）已经拿到真实证据；剩下的 A4 是"一条格式不合规的旧数据"造成的不可达，**等正式数据到位就能自然验证，且验的是真数据**。为它往业务集合写一条人造数据，收益是一条分支，代价是一次不可逆的写入窗口和一次删除核对。

若你仍希望拿到 A4 的云端证据，建议**只做 B1、不做 B2**：B1 一步即可闭环，风险可控；B2 会引入测试投稿与审核动作，属于另一条授权线，不建议与 B1 合并。
