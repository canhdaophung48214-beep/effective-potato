# 决策简报：推广、采集与评分机制

> 项目：微信小程序「山理吃什么」（山东理工大学校园美食推荐）
> 时间：2026-10-20
> 状态：阶段 2 已收尾（v0.2.0），阶段 3 未启动
> 用途：供审查员、规划师复核，确认下一步方向

---

## 0. 一句话结论

校园墙推广暂缓；主线转为**校内真实信息采集**；评分机制从「用户打分」改为**匹配度 + 编辑实测 + 口碑热度**三层，以适配个人主体的合规要求。

---

## 1. 起点与评估结论

最初设想通过校园墙（微信朋友圈/公众号形式的校园信息墙）投放，同时实现四个目的：

| 目的 | 评估结论 | 理由 |
|---|---|---|
| ① 推广小程序 | 有条件可行，但非现在 | 现有 45 道菜 100% 为演示数据，扫码后显示「演示信息」标签，首因效果差；文案若称「已收录全校」属虚假宣传 |
| ② 0.5 元/家收购店铺信息 | 单价设计不合理，模式可行 | 5 毛买不到「到店记录」的劳动（单店约 15–30 分钟），只能买到「抄美团/编价格」的结果，验收成本高于省下的钱 |
| ③ 征集意见 | 可行，性价比最高 | 成本近零，可同时验证需求真伪与市场价格预期 |
| ④ 询问校园墙本人 | 必要 | 掌握渠道与定价权，须先谈后发 |

**用户决定**：④ 与 ① 的推广文案均**搁置**，③ 意见征集稍后考虑，当前主线为**②的校内版本**——收集食堂信息。

**排序结论**：战略上应「先数据、后推广」，因为曝光是一次性的，数据是长期资产。

## 2. 硬约束：个人主体 + 「信息查询」类目

这是本轮最重要的发现，直接改变后续设计。

小程序的**功能必须与所选类目一致**；判定标准是「内容是否由用户发布且对其他用户可见」。

| 功能 | 是否 UGC | 个人主体 + 信息查询 |
|---|---|---|
| 公开留言板 | 是 | 不可做，类目不符 |
| 社区讨论 / 帖子 / 回复 | 是 | 不可做，需「社交-社区/论坛」类目 |
| 用户打分、写评价 | 是 | 不可做 |
| 用户上传菜品照片 | 是 | 不可做 |
| 私密意见反馈（仅管理员可见） | 否 | 可做 |
| 编辑精选口碑（项目方撰写） | 否 | 可做 |
| 收藏 / 历史（仅本地存储） | 否 | 可做 |

**三条合规替代路径**：
1. 反馈代替留言（提交后仅管理员可见，不进入公开列表）
2. 编辑口碑代替评价（项目方整理，不得署名成用户、不得编造）
3. 社群外置（讨论放微信群/QQ群，小程序只做查询）

**权威依据**：微信公众平台 → 设置 → 基本设置 → 服务类目，每个类目下方直接列出所需资质，以当期提示为准。

## 3. 主体升级路径（个人 → 个体工商户）

| 路径 | 成本 | 时间 | 可解决 | 建议 |
|---|---|---|---|---|
| **个体工商户** | 执照 0 元；微信认证 300 元/年；每年记账申报 | 1–3 工作日 | 企业主体小程序、微信支付、多数类目 | **推荐** |
| 有限责任公司 | 代理记账 2000–3000 元/年 | 3–7 工作日 | 开票、融资、ICP 许可证 | 现阶段过重 |
| 借用他人/学校主体 | 0 元 | 不确定 | 类目齐全 | 不建议，主体与运营者不一致风险高 |

**关键事实**：
- 小程序支持**主体变更**（个人 → 企业），AppID 不变，用户与数据不丢；目标主体须先完成微信认证。
- 小程序**必须完成工信部备案**才能上线；个人主体可备案，但备案的服务内容须与类目一致。
- 「社交-社区/论坛」类目通常需要《增值电信业务经营许可证》（ICP 许可证），门槛含注册资本 100 万元以上，个体工商户基本无法申请——因此**社区功能不适合作为近期目标**。

**建议**：现在不升主体。触发条件为以下任意两条同时成立：周活稳定 300–500；有商家主动付费合作；确认用户真会发布内容；需要微信支付。

## 4. 校内信息采集方案（当前主线）

### 4.1 目标数字

| 指标 | 目标 |
|---|---|
| 食堂覆盖 | 6 个（校内全部） |
| 窗口覆盖 | ≥ 50 个（须有真实招牌名） |
| 菜品条数 | ≥ 240 道（每窗口 ≥ 4 道） |
| 价格准确率 | ≥ 95%（抽查 3 家 × 5 道菜与菜单牌一致） |
| 字段完整率 | 100%（名称/价格/楼层/窗口/口味/主食类型） |
| 菜单照片 | 每窗口 ≥ 1 张，命名规范 |

### 4.2 执行顺序

先由项目负责人**独立完成一个食堂的一层**作样板（约 30 分钟），跑通「表格 → 脚本 → 导入 data/*.js → 页面显示」链路，再招人按层分派。

顺序：一号食堂 → 二号 → 三号 → 清真 → 东区 → 教工，每完成一个食堂验收一次。

### 4.3 表格结构（两张表，一行一记录）

**窗口表**：食堂 / 楼层 / 窗口名 / 主营 / 营业时间 / 有菜单牌 / 照片文件名 / 采集人 / 采集日期 / 验收状态

**菜品表**：食堂 / 楼层 / 窗口名 / 菜品名 / 价格(元) / 规格 / 口味 / 主食类型 / 备注 / 采集人 / 采集日期

两条硬规则：
1. **价格不同必须拆行**，不得写「12–15 元」。
2. **口味只填一个**（清淡 / 微辣 / 麻辣），按默认出餐口味；同价不同口味可拆两行。
3. 主食类型限定 8 个枚举值（饭 / 面 / 米线 / 粉 / 饺子 / 麻辣烫 / 面点 / 其他），使用下拉框，避免手打出错。

### 4.4 定价与结算

| 方案 | 价格 | 交付要求 |
|---|---|---|
| **按层包干（推荐）** | 10 元 / 层 | 该层全部窗口 ≥ 4 道菜 + 每窗口 1 张菜单照 |
| 按窗口计价 | 2 元 / 窗口 | 同上 |
| 复核 | 1 元 / 窗口（抽 50%） | 另一人核对 3 个价格 |

预算：约 7 层 × 10 元 + 复核 30 元 ≈ **100 元**，产出约 240 道真实菜品。

结算规则：验收通过后**周结**，微信转账；驳回可改一次，二次不合格该层不付款；每人上限 3 层/周；重复提交不重复计费。

### 4.5 验收与造假识别

| 造假特征 | 核查方式 |
|---|---|
| 无菜单照片 | 一律驳回（唯一硬门槛） |
| 价格与美团完全一致 | 食堂价通常低于外卖价，抽查 3 道对照片 |
| 菜名过于规范 | 食堂写法更口语，过分正式疑为抄录 |
| 一层覆盖全部品类 | 单一窗口不应同时卖炒菜、饺子、麻辣烫 |
| 窗口名写成「X 号窗口」 | 要求补真实招牌名 |

### 4.6 图片资产规范

```
c01_f1_t2_menu.jpg    一号食堂 1 楼 2 号窗口 菜单照
c01_f1_t2_01.jpg      该窗口第 1 道菜实拍
```

真实数据建议用 `c` 前缀编号，与现有演示数据的 `s01–s12` 区分。

### 4.7 十天排期

| 天 | 动作 |
|---|---|
| D1 | 自行走一号食堂 1 楼，建表并填样板 |
| D2 | 编写导入脚本，打通到页面显示 |
| D3 | 招募 3 人，发放任务卡 |
| D4–6 | 采一号 + 二号食堂（约 120 道菜） |
| D7 | 验收 + 首次结算 |
| D8–9 | 采三号 + 清真 + 东区 + 教工（约 120 道菜） |
| D10 | 全量验收、导入、替换演示数据 |

## 5. 评分机制重构（合规替代「用户评分」）

### 5.1 三层结构

| 层 | 含义 | 数据来源 | 合规性 |
|---|---|---|---|
| **匹配度 M** | 菜品与用户当前条件的契合度 | 算法，使用已有价格/口味/类型 | 无 UGC |
| **编辑实测 E** | 项目组实地试吃打分 | 项目方录入，署名「编辑实测」 | 编辑内容 |
| **口碑热度 H** | 被提到的次数（仅数字） | 线下问卷统计聚合 | 聚合统计 |

三层互不冒充，页面上分别标注来源。

### 5.2 匹配度公式

```
M = 0.45 × 预算契合 + 0.35 × 口味契合 + 0.20 × 类型契合
```

- 一致 → 1.0；用户选「不限」→ 0.6；相邻口味（微辣 vs 麻辣）→ 0.5

### 5.3 编辑实测打分与聚合

四维度各 1–5 分：口味 40% / 性价比 30% / 分量 15% / 出餐速度 15%。

```
单人得分 s = 0.4·口味 + 0.3·性价比 + 0.15·分量 + 0.15·速度

聚合 S = (C·m + Σ w_i·s_i) / (C + Σ w_i)
  C = 5        先验强度
  m = 3.8      全库均值
  w_i = 0.5^(距今天数 / 180)   半衰期 180 天
```

示例：1 人打 5 分 → 4.00；3 人打 5 分 → 4.25；20 人打 5 分 → 4.76。

**展示门槛**：Σw < 2 → 不显示分数，显示「编辑初评 · 待更多试吃」；Σw ≥ 5 → 显示「N 人试吃 · 更新于 YYYY-MM」。

### 5.4 口碑热度的边界

- 只公布「本学期被提到 N 次」，不公布原句、不署名、不截图
- N ≥ 3 才显示
- 每学期清零重算

### 5.5 排序规则

**约束**：评分只影响结果集内部的顺序，绝不改变筛选结果集。

```
推荐优先分 = 0.6 × S + 0.4 × (M × 5)
```

无实测数据的菜品，S 取先验均值 3.8（不因「无数据」被抬高或压低）。

示例：酸辣粉 S=4.2、M=92% → 4.36；麻婆豆腐饭无数据、M=95% → 4.18，前者排前。

「查看全部」排序档位由三档扩为四档：默认 / 价格升序 / 价格降序 / 推荐优先。

### 5.6 页面呈现

菜品卡在标签行下方新增一行，无数据时整行不渲染（不影响现有布局）：

```
编辑实测 4.2 · 3 人试吃        匹配度 92%
```

三种状态：有实测+匹配度 / 仅匹配度 / 样本不足显示「编辑初评」。

### 5.7 四条红线

1. 不伪造实测数据（未试吃不得标注「编辑实测」）
2. 不抓取大众点评/美团等第三方评价数据
3. 不公开问卷原文，只发布聚合次数
4. 样本不足（Σw < 2）不展示分数

## 7. 待审查的问题

1. 采集按「层」包干 10 元是否合理？是否应提高到 15 元以确保质量，还是维持低价 + 高验收淘汰率？
2. 评分三层是否现在就实现，还是等 240 道菜采集完成后再做？
3. 「口碑热度」是否保留？风险在于用户可能误读为用户评价，是否需要改名为「提及次数」或直接砍掉？
4. 是否现在办理个体工商户？还是等周活达到 300–500 再办？
5. 原阶段 3「图片展示与用户上传原型」需改造：用户上传改为项目方录入。阶段顺序是否重排？
6. 采集到的真实数据是**替换**现有 45 道演示数据，还是并存（演示数据保留作回退样本）？
