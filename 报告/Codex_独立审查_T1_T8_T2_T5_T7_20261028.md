### 4.2 P0 缺陷（必须修）

**P0-1 `payload === null` 的 pending 永远不再被标记**

```js
// cloudfunctions/retention/index.js:134
if (!row || row.status !== STATUS.PENDING || row.payload === null || !Number.isInteger(row.rev)) {
  skipped++;
  continue;
}
```

后果：一旦某条 pending 的正文被别的路径清空（例如将来 T-2 清理误跑、或人工删除 payload），`mark` 永远跳过它，该记录将**无限期停在 pending**——直接违反本任务 C 段"pending 到期后不得无限期保持 pending"。测试 B8（`tools/test_retention_mark.js:143`）反而把这一行为写成预期（`已匿名化记录不被覆盖 → pending`），**用测试锁死了缺陷**。

最小修法：

```js
- if (!row || row.status !== STATUS.PENDING || row.payload === null || !Number.isInteger(row.rev)) {
+ if (!row || row.status !== STATUS.PENDING || !Number.isInteger(row.rev)) {
```

同时把 B8 改成"payload 已为空也照常标记为 expired"，并新增"payload 为空且超期"的断言。

**P0-2 查询未按状态过滤，旧记录挤占批次导致饥饿**

```js
// :119-123
.where({ createdAt: _.lt(cutoff) })
.orderBy('createdAt', 'asc')
.limit(policy.batchLimit)
```

后果：查询取的是"所有超期记录里最老的 N 条"，不区分状态。若最老的 N 条都是 `approved`/`rejected`（它们只会被 `skipped++` 跳过），那么更年轻的、真正需要标记的 pending 记录**永远不会进入这一批**；每次触发都重复扫同 N 条，形成饥饿。

最小修法：

```js
- .where({ createdAt: _.lt(cutoff) })
+ .where({ createdAt: _.lt(cutoff), status: STATUS.PENDING })
```

注意：加上后测试的 `approved` / `already_redacted` 用例仍在（它们不再被查询命中，断言"不被覆盖"依然成立），但 `skipped` 的语义会变（只统计 rev 异常等），需同步测试文案。
