## 一、摘要

### 1.1 A 方案（保留期实现）五条结论

1. **现状是"设计已定、实现为零"**：30/90/180 三个数值已由 D-2a / D-2b / D-5 定死（C0:161、:162、:166），但全仓无触发器配置、无清理代码，保留期常量仍是 `pending_confirmation` + `days:null`（`项目/config/ugc.js:53-58`；C0:195）。这也意味着**当前代码"不清理"是刻意的**，任何清理实现的第一步是改这个常量（需授权）。
2. **必须拆成两个独立任务**：第 29 天只改状态（`pending→expired`），第 30 天只清正文、**不读 status**（C0:219、:228）。开工包 T2 卡把两者合成一个函数、并用 `status!=='pending'` 过滤（开工包:89），会让"过期任务漏跑"的 pending 记录永远不被清理，直接违反 30 天期限——该卡写法需修正。
3. **摘要是"逐条 8 字段投影 + 每批一条运行记录"的两次追加，绝不原地改写**；`log_redacted` / `retention_purge` / `retention_mark` / `retention_rotate` 四个 action **必须先入 `LOG_EVENTS` 白名单**，否则 `writeLog` 会把未知 action 静默改写成 `denied`（`cloudfunctions/review/index.js:163`），留痕失真且不报错。
4. **四步流水线的删除前置条件是"批次头已写 + 读回校验通过"**，任一步失败都不删（C0:209②）。物理删除不可回滚，所以本方案设计的是"校验闸门 + 可中断续跑"，不是"事务回滚"——开工包:90 的"校验失败回滚"只能解释为"校验失败就不删"。
5. **最大的隐性风险不是清理失败，而是"清完仍被通过"**：`doApprove` 现在没有 `payload===null` 守卫（`review/index.js:258-332`），第 30 天清掉正文后、若第 29 天任务漏跑而记录仍是 pending，管理员可以把一条空记录"审核通过"。触发器能力、cron 时区、告警可达性、单批上限四项云端事实仍属**待确认**（C0:185-193）。

### 1.2 B 方案（审核通知 + 删除入口）五条结论

1. **"审核没人知道"是 M2 的实质**：全仓无 `subscribeMessage` / `requestSubscribeMessage` / `webhook` / `qyapi` / `sendMail` 调用（唯一命中 `pages/index/index.js:518`、`:710` 的 `_notifyBusy` 与通知无关），管理员唯一感知路径是打开 review 页手动刷新（`pages/review/review.js:35-72`）。
2. **通知主通道建议企业微信群机器人 webhook**（无需模板审核、秒级、免费、只需一个 URL 存环境变量），**兜底为 review 页轮询 + 待审计数徽标 + "上次刷新时间"**；订阅消息因"一次授权只发一条"只适合作补充；邮件为次选；短信/服务号不适用（理由见 B.1 对比表）。
3. **通知必须是旁路**：投稿落库成功后再 best-effort 发送，通知失败只留痕，**不得让用户投稿因通知失败而失败**（与 DESIGN:319"先写 submissions 后写日志"的纪律同构）。
4. **用户自助删除不能塞进 review**：review 的管理员闸门在 ACTIONS 之前（`review/index.js:495-499`），加"例外动作"会破坏 fail-closed 结构（写错一行就整函数对外暴露）；应新增独立云函数 `ugc_self`（`list` / `delete`），身份只取 `OPENID`，归属用 `where({_id, 'submitter.openid': openid})`，"不是你的"与"不存在"统一 404。
5. **页面改动集中在两处**：`pages/profile`（我的投稿列表 + 删除，tabBar 天然可达，`app.json:41-46`）与 `pages/submit` 成功卡（即时反悔）；submit 云函数已返回 `submissionId`（`cloudfunctions/submit/index.js:686`）但前端丢弃（`pages/submit/submit.js:172-181`），这是最小改动点。删除语义直接复用 `doDelete` 的 `rejected(user_deleted)` + 主体匿名化（`review/index.js:437-452`），**不引入第二套状态机**。

### A.1 为什么必须拆成两个任务（而不是一个）

**书面依据**（三处，互相印证）：

- 第 29 天标记过期、第 30 天清正文，**两任务独立**（C0:219）。
- 清理任务按 `createdAt` 直接筛选、**不读 status**（C0:228，R-1.3）。
- 清理任务**不得改** `status` / `review` / `verifyStatus`（C0:245①、:219；DESIGN:272"只删不改状态"）。

**工程理由**（本报告主张，说明为什么这三条不是形式主义）：

1. **失败域不同**。标记过期是"状态变更"，可重跑、可见、可人工干预；清正文是"不可逆的数据销毁"。两者合在一个函数里，标记环节的任何异常（例如并发 409、字段校验失败）都会把销毁一起拖失败——而销毁有硬期限（30 天），不能因为一个可重试的状态写入而违约。
2. **依赖方向不同**。清理不能依赖标记成功。若清理"读 status 且要求已过期"，那么第 29 天任务一旦失败，第 30 天就永远不清——这正是开工包 T2 卡 `status!=='pending'` 过滤的致命点（开工包:89）：**最该被清理的恰恰是"没被成功标记"的那批**。
3. **审计语义不同**。清理要留下 `retention_purge` 逐条留痕（C0:245②）；标记要留 `retention_mark`。混在一个函数里，日志无法区分"因过期而清"与"因到期而清"。

**与开工包 T2 卡的冲突（需负责人裁决 D-A1）**：开工包:89 写的是

> `purge_expired_submissions`（按 `createdAt < now-30d` 且 `status!=='pending'` 标记 expired 并清 payload）+ `rotate_upload_logs`（8 字段摘要→追加 log_redacted→读回校验→删明细）

三处问题：(a) 30 天才标记 `expired`，与"第 29 天"规则不符（C0:219）；(b) `status!=='pending'` 过滤使漏跑的 pending 永不被清理，违反 30 天期限；(c) 一个函数同时改状态 + 删正文，失败边界不清，无法满足"任一步失败不得先删"（C0:209②）。**建议**：拆为 `retention_mark`（T-1）与 `retention_rotate`（T-2）两个入口。

**第 3 行的 `review.decision` 取值需拍板（D-A2）**：DESIGN:209 原口径是 `rejected(reasonCode=expired)`，`decision` 自然为 `reject`；D-6 改成独立 `expired` 状态后，`decision` 是保留 `'reject'` 还是新增 `'expire'`？**建议保留 `'reject'` + `reasonCode='expired'`**，因为 `REASON_CODES` 已含 `'expired'`（`review/index.js:57`），而新增 `decision` 枚举会牵连 `safeView`（`review/index.js:116-133`）与前端映射（`pages/review/review.js:55-69`），属于"为了语义纯洁付出三处改动"。

**第 4–7 行是否 `rev+1`（D-A3）**：建议 **bump**。理由：`transition()` 的 CAS 语义建立在 `rev` 上（`review/index.js:196-202`），文档改了而 `rev` 不变，等于告诉并发写者"什么都没发生"。副作用是管理员在 03:00 之前打开的列表，提交时会拿到 409（`review/index.js:275`）——这恰恰是"请刷新"的正确信号。若负责人认为 409 会干扰审核节奏，可改成不 bump，但需在设计里写明"`rev` 不覆盖清理变更"这一例外。

#### A.2.3 现成缺陷：`doApprove` 没有 `payload===null` 守卫

`doApprove` 的校验只有三处：`rev` 一致（`review/index.js:275`）、`status===pending`（`:276`）、`security.state` 合法（`:278-281`）。**没有一处检查 `payload` 是否还存在**。

于是存在这条路径：

```
第 29 天 T-1 失败（记录仍 pending）
  → 第 30 天 T-2 照常清 payload（按 createdAt 筛选，不读 status，C0:228）
  → 记录：status=pending, payload=null
  → 管理员在 review 列表看到一条空卡片（前端 `it.payload && it.payload.note` 容错不崩，review.js:55-69）
  → 点"通过" → doApprove 一路放行 → 写入 approved
  → 结果：一条没有任何内容、却"审核通过"的记录，且不可复原
```

`doReject` 同理（`review/index.js:334-416`）。**建议**：在 `:276` 的状态检查旁增加 `if (!doc.payload) return fail('SUBMISSION_PURGED', ...)`，并在错误码表补一项（DESIGN:509-528）。这是对项目代码的改动，**需授权**（G-06）。

### A.3 定时触发器方案对比

> 说明：微信云开发定时触发器的**公开文档口径**为"在云函数 `config.json` 的 `triggers` 字段声明，cron 为 7 段（秒 分 时 日 月 周 年），也可在控制台配置"。该口径**未在本环境核实**——仓内无任何触发器文件（A0-2），C0:185-193 明确把"是否支持触发器 / 上限 / cron 语法与时区 / 最小粒度"列为待核实项 #1、#2。下表据此把"待确认"写在对应格子里，不作为事实使用。

| 方案 | 触发方式 | 需要的权限 / 前置 | 时区与粒度 | 失败可见性 | 成本 | 结论 |
|---|---|---|---|---|---|---|
| **1. 云函数定时触发器** | 平台按 cron 调用云函数 | 环境管理员/开发者；需部署权限；需在 `config.json` 写 `triggers` 或控制台配置 | 7 段 cron（外部文档口径）；**时区、最小粒度待确认**（C0 #2） | 平台监控可看调用数/错误数/耗时；**告警配置能力待确认**（C0 #4） | 每日 1–2 次调用，资源消耗可忽略（免费额度待确认） | **推荐**；符合 D-2c"定时触发器"（C0:163） |
| 2. 控制台手动运行 / 运维脚本 | 人工点"测试"或本地脚本 | 控制台权限或云 API 密钥 | 无 | 纯人肉 | 0 | 仅用于首次演练与应急；不能作日常（会漏跑，且漏跑无声） |
| 3. 外部调度器（服务器 cron / 外部 CI 定时） | 外部系统按点调用 HTTP 访问服务 | 需开启云开发 HTTP 访问服务 + 自建鉴权 + 外部资产 | 外部可控 | 外部平台告警 | 新增公网入口与密钥管理；项目当前是否有服务器资产**待确认** | 不推荐：为一天两次任务引入公网入口，攻击面/运维成本都大于收益 |
| 4. 小程序端定时 / 用户进入时触发 | 客户端 `setInterval` 或页面 `onShow` | 无 | 无 | 无 | 0 | **否决**：无人使用即不执行；客户端不可信；且把"删库"入口挂在可反复进入的页面上，与"清理必须服务端可审计"（C0:209②）冲突 |
| 5. 控制台独立"定时任务"产品（若存在） | 平台 | **待确认** | **待确认** | **待确认** | **待确认** | 待确认（C0 #1），不作为推荐，也不排除 |

**选型理由（为什么是 1）**：

1. **唯一能满足"无人值守 + 可审计 + 不引入新攻击面"三点**。清理是数据销毁操作，触发源必须可信、可追溯；每次运行都要留 `retention_rotate` 批次记录（A.5），触发器调用天然带 `requestId`，而外部调度器要么暴露公网、要么自己维护一套鉴权。
2. **成本可忽略**：每日 2 次调用（标记 + 清理），远低于免费额度；真正决定成本的是"单批处理条数 × 云函数执行时长"，而不是调用次数（单批上限见 A.9 D-A11）。
3. **手动方案不能作日常**：漏跑无声，而漏跑的后果是合规违约（正文超 30 天仍在）。手动只保留两个用途：首次 dry-run、故障期补跑。

**调度建议**：两条触发器分开时段，例如标记任务 02:30、清理任务 03:30（北京时间口径待确认；若平台按 UTC 解释，则需换算为 18:30 / 19:30 UTC）。**关键**：首次上线后必须用一次 dry-run 打点核对"实际触发时刻"与日志 `at` 字段（`review/index.js:183` 的 `serverDate`），不要相信文档时区。

### A.4 摘要字段与 `log_redacted` 事件格式

#### A.4.1 保留的 8 个字段

C0:199 定的 8 字段，逐项对应现有 `writeLog` 的产出（`review/index.js:164-187`）：

| # | 字段 | 取值来源 | 含个人信息？ | 说明 |
|---|---|---|---|---|
| 1 | `schemaVersion` | 常量 `1` | 否 | 与 `review/index.js:164` 同值 |
| 2 | `event` | 原 `event` | 否 | `submit` / `denied` / `review_approve` … |
| 3 | `action` | 原 `action` | 否 | 原动作名 |
| 4 | `submissionId` | 原 `submissionId` | 否（内部 id，不含正文） | 关联用 |
| 5 | `day` | 原 `day` | 否 | `YYYY-MM-DD` |
| 6 | `result.code` | 原 `result.code` | 否 | 结果码 |
| 7 | `errorCode` | 原 `errorCode` | 否 | 错误码 |
| 8 | `role` | 原 `actor.role` | 否 | 主体角色（`submitter`/`admin`/`system`） |

**到期清除的字段**（C0:200）：`note`、`target`、`actor.openidHash`、`at`、`requestId`、`rev`、`result.stats`。

> 注意：`at` 被清除后，"这条日志发生在几点"就只剩 `day` 的日粒度。这是 C0 的既定取舍（8 字段里没有 `at`），不是本方案引入的损失。

#### A.4.2 两种落地形态（存在歧义，需负责人拍板 D-A4）

| 形态 | 做法 | 优点 | 缺点 | 与 C0 的关系 |
|---|---|---|---|---|
| **甲：逐条 1:1 投影** | 每条待清理明细 → 追加 1 条 `log_redacted`（8 字段） | 可逐条追溯；删前可精确对账；失败可续写 | 条数与明细相同（但每条只有 8 字段，体积小） | 对应 R-2.1"8 字段摘要"（C0:247），但与 R-2.3"追加**一条**"（C0:202-207）字面不符 |
| **乙：批次单条** | 每批 → 追加 1 条 `log_redacted`，带 `stats{count}` | 写入最少；批次审计直观 | 删掉明细后**无法回答"某条投稿在 7 月 3 日被谁审核过"**，审计可追溯性断链 | 严格符合"一条"，但与 8 字段设计意图矛盾 |

**本报告推荐：甲 + 一条批次运行记录**。理由：8 字段里含 `submissionId`，说明设计意图就是"每条留一个可关联的最小投影"；如果只留批次条数，`submissionId` 这个字段就没有存在意义。C0:202-207 的"一条"应理解为"每个批次流程追加事件"，而不是"整批只留一行"。

#### A.4.3 推荐格式（示例）

四个新 action，职责单一（`LOG_EVENTS` 按 `action` 白名单匹配，见 `review/index.js:163`）：

```jsonc
// ① T-1 标记过期：每标记一条，追加一条（不读/不写 payload）
{
  "schemaVersion": 1,
  "event": "retention_mark",
  "action": "retention_mark",
  "submissionId": "sub_abc",
  "day": "2026-10-29",
  "result": { "code": "OK" },
  "errorCode": "",
  "role": "system"
}

// ② T-2 逐条投影：每条待清理明细 → 一条（只含 8 字段 + 溯源 id）
{
  "schemaVersion": 1,
  "event": "log_redacted",
  "action": "log_redacted",
  "submissionId": "sub_abc",
  "day": "2026-07-01",
  "result": { "code": "OK" },
  "errorCode": "",
  "role": "admin",
  "sourceLogId": "log_xyz"          // 见 D-A5，是否允许作为第 9 字段
}

// ③ T-2 批次运行记录（prepare / complete 各一条，append-only 下的状态机）
{
  "schemaVersion": 1,
  "event": "retention_rotate",
  "action": "retention_rotate",
  "submissionId": null,
  "day": "2026-10-29",
  "result": {
    "code": "OK",
    "stats": {
      "phase": "prepare",            // prepare | complete
      "batchId": "R20261029",
      "windowStart": "2026-07-31T03:00:00.000Z",
      "windowEnd": "2026-08-01T03:00:00.000Z",
      "scanned": 120, "projected": 120, "skipped": 0, "purged": 0, "failed": 0
    }
  },
  "errorCode": "",
  "role": "system"
}

// ④ T-2 逐条清理：每条被清明细 → 一条（C0:245② 明确要求）
{
  "schemaVersion": 1,
  "event": "retention_purge",
  "action": "retention_purge",
  "submissionId": "sub_abc",
  "day": "2026-10-29",
  "result": { "code": "OK", "stats": { "cleared": ["note","target","actor.openidHash","at","requestId","rev","result.stats"] } },
  "errorCode": "",
  "role": "system"
}
```

**两个设计要点**：

- **为什么"批次头"要分 prepare / complete 两行**：`upload_logs` 禁止 update（`schema.upload_logs.json:65-68`），而"这批删成功了没有"必须在事后可查。append-only 下没有"更新状态"，只有"追加新状态"——所以 prepare 行写计划，complete 行写结果，**以"最后一条 complete 行"为准**。这不是冗余，这是事件溯源。
- **为什么批次统计放 `result.stats` 而不新增顶层字段**：`result.stats` 是 `writeLog` 已有字段（`review/index.js:172`），且 8 字段剔除清单里明确说"到期清 `result.stats`"（C0:200）——它本来就不是长期保留字段。用在 `retention_rotate` 这种"运行元数据"上行之有效；但**不要**把运行统计塞进逐条投影行，否则 90 天后会被当正文期数据清掉。

#### A.4.4 四条纪律

1. **只 add，不 update/remove 原记录**：C0:209①；`review/index.js:192`；`schema.upload_logs.json:65-68`。摘要是"新写一条"，不是"把旧记录改小"。
2. **三个新 action 必须先入 `LOG_EVENTS` 白名单**：否则 `writeLog` 的 `LOG_EVENTS.indexOf(entry.action)!==-1 ? entry.action : 'denied'`（`review/index.js:163`）会把 `log_redacted`/`retention_purge`/`retention_mark`/`retention_rotate` **静默改写成 `denied`**——不抛错、不告警，只是留痕全错。这是本方案最容易踩的坑，必须配一条单测断言。
3. **三处 `writeLog` 副本必须同步**：`review/index.js:155-158`、`submit/index.js:205-208`，以及新函数。建议加测试断言"三份 `LOG_EVENTS` 数组完全相等"，否则未来必然漂移。
4. **90 天窗口查询必须排除自身产物**：`event in ['log_redacted','retention_run','retention_purge','retention_mark']` 的四类行不得进入下一轮轮转。否则今天的摘要会在 90 天后被再摘要一次，而摘要自身有 180 天保留期（C0:166、:209④）——形成递归，批次证据自噬。

### A.5 四步流水线与失败处理

#### A.5.1 正常路径（每次运行）

```
0. 取锁（A.6）——拿不到直接退出并留痕
1. 选窗口：at < now-90d 且 event 不在自身产物集合中，按 at 升序，限批上限 N（A.9 D-A11）
2. 扫描 N 条明细，逐条生成 8 字段投影（内存）
3. 逐条 add 投影行（action=log_redacted）
4. 读回校验：按 sourceLogId 逐条 get，校验存在且 8 字段一致；再核对计数
5. 写批次头 prepare 行（action=retention_rotate, phase=prepare, stats）
6. 按 _id 白名单逐条 remove 明细（每删一条写一条 retention_purge）
7. 写批次尾 complete 行（phase=complete, stats{purged, failed}）
```

**关键顺序约束：`log_redacted` 全部写成功 → 读回通过 → 写 prepare 批头 → 才允许删。** 删除的唯一前置条件是"批头存在且读回通过"，因为批头是"这批投影已经完整"的原子标记。若批头写在投影之前，一旦投影中途失败，批头会撒谎。

#### A.5.2 失败处理表

| 步骤 | 失败情形 | 检测 | 处置 | 是否已删明细 | 后续 |
|---|---|---|---|---|---|
| 0 取锁 | 锁未释放（上一轮未结束） | 条件更新 `updated===0` | 写 `retention_rotate`（`code=LOCKED`）后退出 | 否 | 下一轮再试 |
| 0 取锁 | 写锁失败 | 异常 | 直接退出（不写日志，避免日志风暴）；由心跳发现 | 否 | 人工 |
| 1 扫描 | 读库失败 / 超时 | 异常 | 写 `retention_rotate`（`code=DATABASE_ERROR`, phase=prepare）后退出 | 否 | 重跑 |
| 2 生成投影 | 数据形状异常（缺 `submissionId` 等） | 逐条校验 | 跳过该条并计入 `skipped`，**不删该条**；批次继续 | 否 | 人工核查该条 |
| 3 写投影 | 单条 add 失败 | 异常 | 立即停止；已写的投影保留（靠 `sourceLogId` 去重续写）；**不写批头** | 否 | 重跑续写 |
| 3 写投影 | 部分成功后函数超时（无返回） | 平台超时 | **无批头 → 第 6 步永不执行**；已写投影留待下次去重 | 否 | 重跑续写 |
| 4 读回校验 | 条数不符 / 字段不符 / 读失败 | 自查 | 写 `retention_rotate`（`code=VERIFY_FAILED`）+ **不写批头** | 否 | 重跑 |
| 5 写批头 | 失败 | 异常 | 无批头 → 不删 | 否 | 重跑 |
| 6 删明细 | 部分 remove 失败 | 逐条 `removed` 计数 | 停止；写 complete 行（`stats.failed>0`）；已删部分**不可回滚** | **部分** | 重跑仅处理残留（幂等） |
| 6 删明细 | 全部成功 | — | 写 complete 行（`failed=0`） | 是 | — |
| 7 收尾 | complete 行写失败 | 异常 | 数据已删但无终态；下次 prepare 对账时可见"已投影且已删"的窗口 | 是 | 人工对账 |
| 横切 | 任何一步失败 | — | **不得先删**（C0:209②）；**不得静默 catch**，必须留 `retention_rotate` 行 | — | — |

**必须说清的一点**：这里没有"回滚"。物理删除不可逆，"校验失败回滚"在语义上只能等于"校验失败就不删"（开工包:90 的措辞需按此理解，否则会被误读成"删了还能恢复"）。设计上真正保证安全的是两道闸：**批头**（证明投影完整）与**读回校验**（证明投影可读）。两者任一缺失，删除步骤根本不启动。

#### A.5.3 单批上限（为什么必须有）

云函数的执行时长与内存上限未核实（C0 #3），而"一次删几千条"既可能超时、又会让失败域变大。建议：单批最多 `N=200` 条（或按实测超时反推），未处理完的留到下一轮；`retention_rotate` 的 prepare 行记录 `scanned`，下一轮从窗口起点继续，直到 `scanned=0`。**不设上限的方案不可部署**——超时会导致"投影写了一半、批头没写、明细没删"的半成品状态反复出现。

### A.6 幂等与重跑

| 机制 | 做法 | 为什么 |
|---|---|---|
| **运行锁** | 单文档 `_id='retention_lock'`，字段 `{owner, lockUntil, lastRotateAt, lastMarkAt}`；用条件更新 `where({_id, lockUntil: _.lt(now)})` 获取——复用 `transition()` 的 CAS 思路（`review/index.js:196-202`） | 触发器重试、手动补跑、部署期双实例都可能并发；两个清理任务同时跑会重复写投影 |
| **锁的载体** | 必须新增集合（如 `retention_state`） | `upload_logs` 禁止 update（`schema.upload_logs.json:65-68`），锁需要 update；这是**硬约束**，不是偏好（D-A6） |
| **投影去重** | 每条投影带 `sourceLogId`，写前按 `sourceLogId` 查重；已存在则跳过写入，直接进入删除判断 | 断点续跑时不产生第二份摘要 |
| **删除幂等** | `remove` 不存在的 `_id` 返回 `removed:0`，视为成功 | 部分删除后重跑，已删的不报错 |
| **批号** | `R<YYYYMMDD>`，UTC 日（与 `day` 口径一致，`review/index.js:183`） | 同一窗口重跑共用批号，便于对账 |
| **完成判定** | 存在同批号 `phase=complete` 且 `failed=0` 的 `retention_rotate` → 跳过 | 避免重复扫描 |
| **计数自洽** | `scanned = projected + skipped`；`purged + failed = scanned`；不自洽则不删 | 第 6 步前的最后一道账目核对 |
| **重跑收敛性** | 任意时刻中断后重跑，终态唯一：不重复投影、不重复删、不丢明细（未删的仍在窗口内） | 这是"可重跑"的定义，也是测试要断言的东西（开工包:90） |

**一个边界必须写进测试**：如果第 6 步删了一半，而第 7 步 complete 没写成，下一轮 prepare 会看到这些明细"已有投影、且 at 仍在窗口内"。此时正确行为是**跳过投影、直接删**（投影已存在），而不是重新生成。若实现成"窗口内一律重新投影"，会产生重复摘要行——这是最可能被忽略的幂等 bug。

### A.7 监控与告警

清理任务的特点是"**失败了没人知道，且失败后果是合规违约**"（正文超期仍在），所以监控设计要优先解决"如何发现它没跑"，而不是"如何看它的输出"。

| 层 | 手段 | 能发现什么 | 覆盖不到的 |
|---|---|---|---|
| L1 运行留痕 | 每轮至少 2 条 `retention_rotate`（prepare/complete），每条清理 1 条 `retention_purge` | 跑了多少、成功多少、失败多少 | 需要人去查 |
| L2 心跳 | 独立小任务（或同一触发器内的第一步）检查 `lastRotateAt`，超 26h 未成功 → 告警 | 任务停摆 | **心跳自己也停摆时一起静默**（自杀问题） |
| L3 平台告警 | 云开发控制台对云函数配"错误数/超时"告警 | 函数级故障 | 能力待确认（C0 #4）；且"函数成功但一条没处理"不会被发现 |
| L4 管理端可见 | `review` 的 `session`/`list` 返回值附带"最近一次保留期运行时间 + 状态"，管理员打开即看到红/黄/绿 | 低频但真实的停摆；不依赖任何外部渠道 | 需要改 review（代码授权） |
| L5 人工对账 | 每周核对：`retention_purge` 条数 ≈ `log_redacted` 条数 ≈ `submissions` 中 `payload=null` 的条数 | 账目偏差、静默漏删 | 滞后一周 |

**为什么推荐先做 L4**：它零外部依赖、零费用、不依赖"是否申请了模板/是否建了企业微信群"，却能覆盖最关键的失败模式（任务连续几天没跑）。通知渠道再花哨，也不如"审核员每天必然打开的那个页面"上有一行红字。

**"自杀问题"必须如实承认**：如果触发器被禁用或配置错误，L1/L2/L4 全都不产生新数据——唯一能发现的是 L3 平台级监控，或管理员注意到 L4 的"最近运行时间"停在三天前。因此 L4 的展示必须包含**时间**而不只是状态灯（"3 天前"比"绿色"更能暴露问题）。

**告警分级建议**：

- P1（当天处理）：连续 2 天无 complete 行；`failed` 占比 > 10%。
- P2（本周处理）：单条 `skipped`（数据形状异常）；`LOG_FAILED`。
- 不告警：`LOCKED`（正常并发退让）。

**M2 的准确描述**：不是"没有通知功能"，而是"**管理员必须主动想起去看，否则新投稿无限等待**"。这决定了方案的优先级：先解决"提醒存在"，再解决"提醒好看"。

### B.1 管理员通知渠道对比

| 渠道 | 前置 / 审批 | 到达时效 | 能覆盖"没打开小程序" | 实现面 | 成本 | 结论 |
|---|---|---|---|---|---|---|
| **1. 企业微信群机器人 webhook** | 企业微信群 + 机器人 URL（密钥）；云函数出网能力**待确认** | 秒级 | 是 | 云函数 HTTPS POST；URL 存环境变量，不入库 | 免费 | **推荐主通道** |
| **2. 管理端轮询** | 无 | 取决于打开频率 | 否 | 纯前端（`onShow` + `setInterval` + `onHide` 清理） | 0 | **必备兜底** |
| 3. 订阅消息（一次性） | 公众平台申请模板（类目审核）；**每次发送前需用户点击授权，一次授权仅一条** | 秒级 | 是（受额度限制） | 云函数 `subscribeMessage.send` + `config.json` 声明 openapi + 前端 `wx.requestSubscribeMessage`（需用户手势） | 免费 | 仅作补充：额度=管理员点击次数，无法支撑"每条投稿都通知" |
| 4. 长期订阅消息 | 仅特定类目开放，**本项目类目是否具备待确认** | 秒级 | 是 | 同上 | 免费 | 待确认，不作为方案基线 |
| 5. 邮件（SMTP / 第三方） | SMTP 凭据或第三方邮件服务 + 发信域名 + 出网 | 秒~分钟 | 是 | 云函数出网 + 密钥；垃圾箱风险 | 第三方可能收费 | 次选 |
| 6. 短信 | 签名/模板审核 + 手机号（**两表不含手机号**，DESIGN:197） | 秒级 | 是 | 需第三方 | 按条计费 | 不适用 |
| 7. 服务号模板消息 | 需服务号 + 用户关注 | 秒级 | 是 | 小程序无法直接发 | — | 不适用 |

**为什么主推企业微信而不是订阅消息**（这是本方案最需要说清的取舍）：

- 订阅消息的授权模型是"**一次点击换一条消息**"。管理员要在收到 N 条通知前，先点 N 次"允许"。这在小程序里是硬限制，不是实现问题。用它做"每条投稿通知"，等于要求管理员每天点几十次授权。
- 企业微信机器人只需要一个群和一个 URL：`POST` 一段 markdown 就到群里，无模板审核、无授权次数、无限量（合理频率下）。代价是"负责人得有一个企业微信群"——这是一个组织问题，不是技术问题，所以列进授权清单（G-11）。
- 如果两者都不具备（没有企业微信、也不想申请模板），方案仍然成立：**P0 轮询**能保证"打开就能看到"，代价是"没打开就不知道"——这必须如实告诉负责人，不能包装成"已解决"。

### B.2 最小实现与降级链

| 级别 | 内容 | 前置 | 覆盖度 | 结论 |
|---|---|---|---|---|
| **P0** | review 页 `onShow` 刷新 + 5 分钟轮询（`onHide` 停止）+ 待审计数徽标 + "上次刷新 HH:mm" | 零授权 | 打开页面即可见；没打开则无感 | **先做**，永远保留 |
| **P1** | submit 落库成功后 best-effort 通知：读 `ALERT_WEBHOOK_URL`，有则 POST 企业微信，无则跳过 | 环境变量 + 云函数（代码授权） | 秒级、覆盖离线 | 推荐（若负责人建群） |
| **P2** | 订阅消息：管理员在 review 页点"开启提醒"，`requestSubscribeMessage` 拿一次额度 | 模板审批 + `config.json` 权限 + 前端手势 | 一次授权一条 | 可选补充 |

**P1 的实现纪律（三条）**：

1. **旁路**：通知在 `submissions` 落库成功之后发送，`try/catch` 包住，失败只写一条日志，**绝不改变投稿返回结果**。用户投稿成功与否，与管理员收不收得到通知无关。（与 DESIGN:319"先写 submissions 后写日志"同构：业务先行，旁路后行。）
2. **不重试**：通知失败不重试、不排队。理由：通知的价值是"及时"，5 分钟后重发一条"有新投稿"意义不大，而队列会引入新的状态与失败面。失败靠 L4 的"待审计数"补偿——管理员打开页面仍能看到。
3. **可关闭**：无 `ALERT_WEBHOOK_URL` 时静默跳过，不报错、不刷日志。这样"没配置"和"配置了但坏了"在日志上可区分（后者会有失败记录）。

**通知内容建议**（只放最少信息，不放正文）：`新投稿待审：1 条；类型：价格纠错；提交时间：10-28 14:20；请到「审核」页处理`。**不放 note 正文**——通知渠道是第三方，正文一旦外发就脱离了 30 天保留期的控制范围。这是保留期方案（A）对通知方案的硬约束。

### B.3 用户自助删除：鉴权设计

#### B.3.1 四个可选形态

| 形态 | 改动面 | 安全性 | 结论 |
|---|---|---|---|
| **A. 在 `review` 里加 `delete_self` / `mine`，把闸门改成"白名单例外"** | 改 1 个函数 | **破坏 fail-closed**：闸门目前先于 ACTIONS（`review/index.js:495-499`），例外写错一行就整函数对外暴露；且 403/404 语义会混乱 | **否决** |
| **B. 新增云函数 `ugc_self`（`list` / `delete`）** | 新函数（`app.json` 无需改） | 独立权限、独立测试、完全不碰 review 的闸门 | **推荐** |
| C. 维持现状（客服代操作 + 页面文案说明） | 0 代码 | 最安全 | 兜底；但 D-3 渠道未接入（C0:164），且要求 24h 内人工处理（DESIGN:496-501） |
| D. 在 `submit` 里加 `action='delete'` | 改 1 个函数 | `submit` 当前只接受 `action==='submit'`（`submit/index.js:486-493`），扩 action 会打破"提交函数只提交"的边界；且它的 openapi 权限（内容安全）与删除无关 | **否决** |

**为什么形态 A 不可接受（这是本方案的核心安全论点）**：`main` 现在的顺序是

```js
// review/index.js:495-499（示意）
if (!checkAdmin(event)) return fail('FORBIDDEN', ...);   // 闸门
if (ACTIONS.indexOf(action) < 0) return fail('INVALID_ACTION', ...);  // 行动白名单
```

即"**先验身份，再看你要干什么**"，且未授权时零数据库调用。这个顺序的价值是：即使行动白名单被写错，也不会越权。一旦为了"用户自助"把顺序改成"先看 action，若是 `delete_self` 就跳过管理员校验"，那么"某个 action 忘了加回管理员校验"就变成一条真实的越权路径，而且它是**未来每一次改这个函数时都要重新判断一次**的负担。独立函数把这个判断变成一次性的、可测试的、物理隔离的。

#### B.3.2 推荐形态：独立云函数 `ugc_self`

```
函数：ugc_self（部署名以 config 为准）
actions：list（我的投稿列表） / delete（删除我的一条）
身份：cloud.getWXContext().OPENID（唯一来源）
权限：无 ADMIN_OPENIDS、无 openapi 需求
数据：submissions（读己方、写 own）、upload_logs（追加 delete_request）
```

**为什么不复用 `review.delete` 的代码而是"复用语义"**：`doDelete`（`review/index.js:419-483`）的写入形状是 `payload=null` + `submitter.openid='deleted'` + `status=rejected` + `review.reasonCode='user_deleted'` + `rev+1`，这套形状**必须逐字段复制**，否则同一条记录会因"谁删的"而呈现两种状态，管理员侧无法统一处理。建议把这段 patch 逻辑抽成新函数里的独立方法（复制而非 import：云函数目录不共享模块，除非另建层/包——**待确认**项目是否接受共享包）。

#### B.3.3 七条校验

| # | 校验 | 做法 | 依据 / 理由 |
|---|---|---|---|
| 1 | 身份只取 `OPENID` | `cloud.getWXContext().OPENID`；空 → 401 `NO_OPENID` | 与 `submit/index.js:495-497` 同构；绝不接受客户端传 `openid` |
| 2 | 归属 | `where({_id: id, 'submitter.openid': openid})`，查不到 → **404** | "不是你的"与"不存在"**统一 404**，防枚举；与 `review/index.js:241-256` 的 detail 404 同风格 |
| 3 | 动作白名单 | 仅 `list`/`delete`，其余 `INVALID_ACTION` | 与 `submit/index.js:486-493` 同风格 |
| 4 | 幂等 | 已是 `rejected` 且 `review.reasonCode==='user_deleted'` → 200 `{idempotent:true}` | 逐字复用 `review/index.js:431-433` 的判定 |
| 5 | 频控 | 按 `openid` 每小时 N 次（复用 `ix_submitter_created` 查询思路，`schema.submissions.json:103-108`） | 防脚本枚举与误删风暴 |
| 6 | 审计 | 写 `delete_request`，`actor.role='submitter'`，`openidHash` 同盐同算法 | `review/index.js:99-101`、`:462-472`；否则同一用户在两处留下不同 hash |
| 7 | 单条 | 一次只接受一个 `submissionId`，不支持批量 | 批量删除是误删与滥用的放大器，且当前无此业务需求 |

#### B.3.4 与现有删除路径的语义对齐

| 维度 | 管理员 `review.delete` | 用户 `ugc_self.delete` | 是否一致 |
|---|---|---|---|
| `payload` | `null` | `null` | ✅ |

### B.5 失败与越权处理

| 场景 | 后端返回 | 前端表现 | 自动重试 | 备注 |
|---|---|---|---|---|
| 未登录（无 `OPENID`） | 401 `NO_OPENID` | "登录态失效，请重新进入小程序" | 否 | 与 submit 一致（`submit/index.js:495-497`） |
| 不是本人 / 不存在 | 404 `NOT_FOUND` | "没找到这条投稿" | 否 | 统一 404 防枚举 |
| 已删除 | 200 `{idempotent:true}` | "已删除" + 刷新列表 | 否 | 幂等（`review/index.js:431-433`） |
| 数据库异常 | 500 `DATABASE_ERROR` | "稍后再试" | 手动 | — |
| **删除已生效但写日志失败** | 500 `LOG_FAILED` | "已删除，但记录写入异常，请联系客服" | **否** | 幂等分支不会补写日志，重试无意义（见下） |
| 频控 | 429 `RATE_LIMITED` | "操作过于频繁" | 否 | — |
| 网络失败 | —（无响应） | 不改本地状态，按钮保留可再点 | 手动 | 避免"看起来删了其实没删" |

**关于 `LOG_FAILED` 的诚实处理（重要）**：`doDelete` 的幂等分支在"已删除"时**直接返回，不写日志**（`review/index.js:431-433`）。这意味着"删除成功但日志失败"的记录，重试永远不会补上审计行。所以：

- 前端必须告诉用户"**已删除**，但记录写入异常"——不能显示"删除失败"诱导重试（重试也是 500）。
- 运维侧需要一条补偿路径（人工补 `delete_request` 行，或在问题清单登记），否则审计链会留下一个无法自愈的洞。这一点建议在实现时明确（**D-B3**）。

**越权专项**：

| 攻击面 | 处置 |
|---|---|
| 传别人的 `submissionId` | 404；同时写 `denied` 日志（role=submitter）以便发现扫描行为，并计入频控 |
| 客户端伪造 `openid` 字段 | 服务端**不读**该字段，只认 `getWXContext()` |
| 批量/脚本刷删除 | 频控 + 单条限制 + 404 统一（无法通过响应差异判断存在性） |
| 删除后重投"洗白" | `dedupe` 只挡 `pending`（`submit/index.js:566-576`），删除后 `status=rejected` → 同内容可重投。**建议**：`rejected` 的 `dedupe.key` 也保留一段时间，提交时提示"该内容近期已被驳回"（**D-B4**） |
| 删除已通过内容 | 设计允许（DESIGN:496-501）。当前不影响任何展示（B0 核实：社区页无云端读取，`cloudRepo.js:43-47` 白名单只有 restaurants/stalls/dishes）；但将来社区若读 submissions，必须另建"已发布快照" |
