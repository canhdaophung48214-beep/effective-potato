## ② 逐项证据

### 2.1 T233 —— `checkDirFsync` 可用分支

**用例现状**（`项目\tools\test_records_spec.js:4514-4534`）：

```
4519:  const cap = I.checkDirFsync(dir);
4520:  const r = I.initIdMap('{"schemaVersion":1}\n', target);
4522:  if (!cap.ok) {                        // ← 本机只走这一支
4523:    if (r.status === 'INIT_FSYNC_UNAVAILABLE' && r.wrote === false && exists === false && r.exitCode === 3)
4528:  } else if (r.status === 'INIT_OK' && exists && fs.readFileSync(target,'utf8') === '{"schemaVersion":1}\n') {   // ← 从未在本机执行
```
断言对象：`initIdMap` 的返回对象（`status/wrote/exitCode`）+ 目标文件是否存在 + 读回内容。使用**真实 fs**（`mkdtemp` 在 `%TEMP%`），无替身。

**实现分支**（`项目\tools\pilot\gen_records.js`）：
- `checkDirFsync(dir)` `:2157-2168`：`fd = fs.openSync(dir,'r')` → `fs.fsyncSync(fd)` → `{ok:true}`；`catch` → `{ok:false, code:e.code||'UNKNOWN'}`；`finally` close。**无平台分支、无降级**。
- `fsyncDirNow(dir, phase, opts)` `:2173-2180`：有 `opts.__testDirFsyncNow` 则调替身，否则 `return checkDirFsync(dir)`。
- `initIdMap`：`:2186` 目标存在→`INIT_TARGET_EXISTS`（**先于**能力探测）→ `:2190` 探测失败即 `:2192 INIT_FSYNC_UNAVAILABLE`（`wrote:false`）→ 之后才是写 tmp/link/两次目录 fsync。

**本机实测（命令见 §6）**：
```
{"dir":"C:\\Users\\25975\\AppData\\Local\\Temp\\t8probe-rckJOz","open":"OK","fsync":"EPERM","cleaned":true}
node=v26.5.1 platform=win32
checkDirFsync(工具目录) = {"ok":false,"code":"EPERM","message":"目录级 fsync 不可用：EPERM"}
fsyncDirNow_real(tmp)  = {"ok":false,"code":"EPERM","message":"目录级 fsync 不可用：EPERM"}
```
**结论**：本机失败点在 `fsyncSync`（不是 `openSync`，`openSync` 对目录是成功的）。故 `:4528` 的 else 分支在 NTFS 上**不可达**，这一点与审计描述一致，但更精确：不是"打不开目录"，而是"目录 fd 不能 fsync"。

**可补性实测**（关键）：用 `new Function` + 自定义 `require` 注入一个 `fs` 代理，仅把"对目录 fd 的 `fsyncSync`"改成 no-op，其余全部走真实 fs，然后调用 `initIdMap`：
```
inline_keys=validateAttachments,checkDirFsync,fsyncDirNow      ← K3 成立：不改 gen_records.js 也能取到 fsyncDirNow
cap={"ok":true}
init={"status":"INIT_OK","wrote":true,"exitCode":0,"exists":true,"contentOk":true,"residue":["id-map.json"]}
fs_ops=open,dir-fsync-noop,open,dir-fsync-noop,open,write,link,open,dir-fsync-noop,open,dir-fsync-noop
cleaned=true
```
即：**`INIT_OK` 分支在 Windows 本机可被真实执行**（写 tmp / `linkSync` / `unlinkSync` / 读回全部是真实文件系统操作，只有目录 fsync 是代理 no-op）。残留只有 `id-map.json`，无 `.id-map-init-*`。

**边界**：这只证明"控制流分支可达 + 真实写链路正确"，**不证明** NTFS 具备目录 fsync 能力——真实能力分支仍需 ext4（`docs/AUDIT_RECORD_CONTRACT_WSL_PREP_20261025.md:63` 记载 WSL 内 T233 走"合成目录+合成 payload"通道，`docs/AUDIT_RECORD_INIT_IMPL_20261025.md:44` 记 WSL ext4 首次 `INIT_OK`）。

### 2.3 T242 / T242b —— 持久性替身

**用例现状**：
- `T242 :3976-3999`，首行注释即自限定："`initIdMap` 后半段（受控替身：仅测试注入 fsync 探测与目录同步，**不代表本机持久性**）"（`:3976`）；pass 文案再次自注"（不代表本机目录持久性）"（`:3994`）。注入两个替身：`__testFsyncProbe`（返回 `{ok:true,code:'STUB_FSYNC_OK'}`）与 `__testDirFsyncNow`（记录 phase、返回 `{ok:true}`）。**其余全部真实**：`openSync(tmp,'wx')`、`writeFileSync`、`linkSync`、`unlinkSync`、`readFileSync` 读回、二次初始化→`INIT_TARGET_EXISTS` 且不覆盖。
- `T242b :4001-4098`：七个场景（每场景独立 `box(n)` 子目录），首行注释"全部替身注入，**不依赖本机目录 fsync 支持**"（`:4001`）。其中场景 4 是**真实**的（预创建目标→`INIT_TARGET_EXISTS`，`:4050`）。

**实现分支**：`:2218` afterLink 失败→`INIT_DURABILITY_UNCONFIRMED`+`phase:'afterLink'`+`wrote:true`+保留目标与 tmp；`:2224` unlink；`:2226` afterUnlink 失败→同状态；`:2233` 读回不一致→`INIT_RECHECK_MISMATCH`。

**未验证的到底是什么**（三者要分开，否则容易把"不能"说小）：
1. **"真实目录 fsync 在成功方向上被调用过"** —— 本机不可能：`fsyncDirNow` 真实调用实测返回 `EPERM`（§2.1）。`initIdMap` 在本机根本走不到 `:2218`（`：2190` 的探测先失败）。→ **不能补**（需 ext4）。
2. **"fsync 调用真的发出了"** —— 只能靠 instrumentation 断言调用发生（T242 的替身就是在断言"两次调用顺序 `afterLink,afterUnlink`"），**没有**任何合法手段在 Windows 用户态观测到"真正落盘"。
3. **掉电/崩溃语义（fsync 的本来目的）** —— 进程内测不了，任何 mock 都测不了；需 VM 断电实验或 `dm-flakey` 之类块设备注入。→ **不能补**，且不建议为此立项。

**可以补的那一条**：把"真实 `fsyncDirNow` 在本机 fail-closed"固化成断言（`fsyncDirNow(tmp,'afterLink',{})` → `ok:false` + `code:'EPERM'`），并在 ext4 上反转断言（`ok:true`）。这是**单一用例双分支**，价值是防止有人"为了让测试过"给它加静默降级。

### 2.4 T243 —— 源码文本断言

**用例现状**（`:4487-4512`）：
```
bodyOf(name) = src.slice(src.indexOf('function '+name+'('), src.indexOf('\nfunction ', 该位置))
断言1: bodyOf('run')+bodyOf('main')+bodyOf('publishOutputs') 内 'verifyPlanDigest(' 与 'initIdMap(' 均 indexOf < 0
断言2: bodyOf('runInit') 内 cnt('initIdMap(')===1 && cnt('verifyPlanDigest(')===1
断言3: require() 导出键串 === '__test__,run,runInit' 且 Object.keys(g.__test__).length === 9
```
**局限（实证）**：`cnt()` 是纯字符串计数，对**注释和字符串字面量同样敏感**——本次实测中，源码里若出现 `// … 不调用 initIdMap(` 这样的注释，`cnt` 会变 2 而误报。反过来，若把调用改写成 `initIdMap .call(...)` 或别名 `const f = initIdMap; f(...)`，文本断言**会漏报**。这就是"覆盖文本不覆盖行为"的具体危害面，不只是"静态不够优雅"。

**行为化的可行性（有据）**：
- 模块可被外部加载并注入 `require`：实测 `inline_keys=validateAttachments,checkDirFsync,fsyncDirNow`（§2.1），说明 K3 通道可用，且可注入**代理 `fs`** 记录每一个调用。
- `run()` 本身已有**测试专用注入口**：`gen_records.js:672-673`"注入记录时（内部测试通道）不因缺少 id-map.json 提前返回"、`:695` `Array.isArray(opts.records)`；`run()` 在 `:635` 读取 `opts.outDir`，即**可把输出全部导向临时目录**，不触正式产物。
- 更强的行为证据：`NODE_V8_COVERAGE=<dir>` 跑一个子进程（只调 `run({mode:'dry-run'})` 或 `run({mode:'write', outDir: tmp, records: fixtures})`），coverage JSON 里 `functions[].functionName === 'initIdMap'` 的命中计数应为 **0**——这才是"零隐式初始化"的行为证明。
- **前置待确认**：本次**未执行**生成器（避免任何侧写疑虑），因此"`run({mode:'write'})` 在只读仓库 + 临时 outDir 下能干净退出"属**待确认**；`dry-run` 同理。补测落地时先跑一次空跑确认，再固化成用例。
