## 二、必须先认清的输入形状（否则解析器写不出来）

两份转述稿里**只有四类表格**承载菜品数据，另有大量散文段（名册、待确认、裁决、口径）**不得当记录源**。

### 2.1 四类表形态

| 形态 | 表头形态（实测原文） | 语义 | 规则 |
|---|---|---|---|
| **S1** 单值 | `| 菜品 | 价格 |` | 一行一菜一价 | R1 |
| **S2** 双规格列 | `| 菜品 | 小碗 | 大碗 |`（`TRANSCRIPTION_2F.md:355`）、`| 菜品 | 小份 | 大份 |`（`:434`） | 一行 = 2 条，按列拆 | R5 |
| **S3** 多做法列 | `| 口味（现场原文） | 炒饼 | 炒面 | 炒饭 |`（`:260`） | 一行口味 = 3 条，按列拆 | R4 |
| **S4** 多基底列 | `| 口味（现场原文） | 米线 | 牛筋面 | 土豆粉 |`（`:226`）、`| 口味（现场原文） | 砂锅米线 | 牛筋面 | 土豆粉 |`（`:529`） | 一行口味 = 3 条，按列拆 | R3 |

> S3 与 S4 的**首列表头不是「菜品」而是「口味（现场原文）」**——这是识别「按列拆」的唯一可靠信号，不要用「列数 ≥ 3」来猜。

**输入清单（首版，**已批准 D3**）**：只读 `tools/pilot/TRANSCRIPTION_2F.md` 与 `tools/pilot/TRANSCRIPTION_3F.md` 两份转述稿。**首版生成器不得读取独立的 3F 档口名册**（`TRANSCRIPTION_3F.md` 本身没有导览牌名册，2F 的名册只在 2F 文档内）。由此：
- 3F 档口**位置证据不足**的状态不变，仍按 §5.6.3 的候选 ID + 证据阻塞处理；
- 存在 ID 候选 **≠** 位置已核实 **≠** 可导入（三者必须分别表述）。

### 2.2 价格单元格语法（S1 里出现的六种变体，必须逐条显式支持）

| 变体 | 实测原文 | 解析结果 |
|---|---|---|
| 纯价 | `9 元` | 9 |
| 带规格后缀 | `9 元（小份）`（`TRANSCRIPTION_2F.md:70`） | 9，规格 = 小份（**不拆**，S1 里规格是同一条记录的属性） |
| 带单位 | `5 元/个`、`10 元/份` | 5、10 |
| 阶梯内联 | `5 元/个（2 个 9 元，3 个 12 元）`（`TRANSCRIPTION_3F.md:210`） | **拆 3 条**：5 / 9 / 12，规格 = 1 个 / 2 个 / 3 个（R2） |
| 双价 | `17.9 元`、`14.9 元` 分列两行 | 不合并（R1，两条独立记录） |
| 任何解析不出数字的写法 | 例如「时价」「X 元起」 | **硬失败 E4**，不得猜价 |

`## 一、先放官方名册`、`## 二、拍到的 16 家`、`## 四、待确认汇总`、`## 六 / §七 / §八 裁决与口径`、3F 的 `## 三、全批待确认清单`、`## 六、统计口径说明`、`## 七、source_detail 规则`、`## 八、证据缺口`。跳过数量要打印（例如「跳过非记录段 9 段」），**静默跳过等于掩盖解析失败**。

## 三、函数接口（分层，不过度抽象）

### 3.1 分层与纯度

| 层 | 函数（**已冻结签名**，2026-10-24 `G-7=O-1`） | 纯 / IO | 职责 | 失败行为 |
|---|---|---|---|---|
| L0 读取 | `readSource(filePath) → string` | **IO（只读）** | 读两份 md；只允许读入参给定路径 | 抛 `E1_IO` |
| L1 解析 | `parseDoc(text, meta) → { sections, tables, skipped }` | 纯 | 按 `##`/`###` 切段；识别 2.1 的 S1–S4；记录表格行号 | 表形态无法归类 → 进 `unparsable` 列表（不中断） |
| L2 归类 | `classifyTable(table) → 'S1'|'S2'|'S3'|'S4'|'EXCL'` | 纯 | `EXCL` = 套餐表 / 名册表 / 待确认表 | 未知形态 → `E2_UNKNOWN_TABLE` |
| L3 展开 | `expandTable(table, ctx) → Record[]` | 纯 | 执行 R1–R8；价格格用 2.2 的六种解析 | 价格不可解析 → 该行进 blockers，不产出记录 |
| L4 证据 | `buildSourceDetail(record, ctx) → string` | 纯 | 按 §五点四的模板生成；幂等 | 缺照片序号且非「无原图」→ `E6_EVIDENCE` |
| L5 判定 | `judgeGeneration / judgeEvidence / judgeEligibility(record, ctx) → enum` | 纯 | 三个判定**互不推导**（§四） | 枚举非法 → `E3_ENUM` |
| L6 汇总 | `summarize(records) → { total, A, B, C, perStall }` | 纯 | 三元账；`A+B+C === total` | 不闭合 → `E9_SUM` |
| L7 校验 | `assertContract(records, summary) → violations[]` | 纯 | 跑 §4.3（`C17`–`C20`）+ §6.2 规则表所列断言 + 条数断言（原「C1–C16」编号体系未定义，见 §10.7） | 有 violation → 整体失败 |
| L8 写出 | `writeOutputs(payload, opts) → { written, skipped }` | **IO（可写）** | 默认 dry-run；仅在 `opts.write === true` 且路径校验通过时写 | 见 §七 |
| L9 编排 | `run(opts) → { exitCode, summary, violations, blockers }` | 混合 | 串起 L0–L8；**唯一的生产对外入口**（`__test__` 仅测试可见，见 §10.6.4 `G-7`） | 任何硬失败 → 不写任何文件 |

> **纯函数占 7/9**：L1–L7 全部无 IO，可用字符串夹具直接单测；只有 L0 与 L8 碰文件系统。这样 `test_records_spec.js` 里那 4 条「待实现」断言可以在**不写盘**的前提下被满足。

### 3.4 `records_blockers.json` 结构（**已裁决 2026-10-24，C-1=A**）

阻塞清单与 `records.json` 并列输出，结构固定为：

```jsonc
{
  "schemaVersion": 1,
  "count": 2,
  "entries": [
    {
      "recordKey": "f2/W2-04/dancao/青椒蛋|炒饼",
      "stallId": null,
      "name": "青椒蛋炒饼",
      "tier": "B",
      "sourceLine": 262,
      "rawRow": "| 青椒蛋 | 10 元 | 10 元 | 10 元 |",
      "kind": "evidence_gap",
      "reasons": ["B9", "B13"]
    }
  ]
}
```

规则（全部为硬约束）：

- **一条待阻塞记录一条 `entry`**；同一记录的多个原因放进该条 `reasons` 数组，**不得**拆成多条 entry。
- `count` 必须**等于** `entries.length`；不等即 S3 对账失败。
- `entries` 内**不得出现任何时间字段**（`generatedAt`／`createdAt`／`updatedAt`）；引入时间字段会破坏 §7.2.8 的字节哈希稳定性。
- `kind` 取值限定四类：`not_generated`（C 档未生成）／`evidence_gap`（证据缺口）／`blocked_by_decision`（待裁决）／`id_unassigned`（无 `stallId` 导致无 `id`）。
- `reasons` 的元素必须是契约已定义的阻塞编号（`B1`…`B13`）或诊断标识（如 `KEY_COLLISION`），**不得**写自由文本。
- 本文件只记录「**待阻塞**」的记录；已进入 `records.json` 且无阻塞的记录**不得**出现在 `entries` 中。因此 `count` 与 `records.length` **不必相等**，也不得相互推算。

## 四、三类判定必须独立

### 4.1 枚举与判定条件

| 字段 | 合法值 | 判定条件（按顺序） | 不允许的推导 |
|---|---|---|---|
| `generation_status` | `generated` / `not_generated` | 价格可解析 **且** 规则能唯一确定条数 **且** 不属于 R6/R7/R8 排除项 → `generated`；否则 `not_generated` 并写 blockers | **不得**由 `evidence_status` 反推（原图缺失不影响能否生成） |
| `evidence_status` | `traceable` / `missing_original` / `unclear_source` | 有照片序号且该组原图在（按转述稿声明）→ `traceable`；声明原图缺失 → `missing_original`；照片序号本身记不清 → `unclear_source` | **不得**由 `tier` 反推（tier 是综合结论） |
| `import_eligibility` | `blocked` / `candidate_only` | 记录自身或其店铺/窗口命中任一**未解除**阻塞 → `blocked`；否则 `candidate_only` | **不得**出现「已可导入」值——当前 0 条可入 CSV（方案 §四 / 3F §八） |

### 4.2 三者的合法组合（A / B / C 档的定义落在这里）

| 档位 | `generation_status` | `evidence_status` | `import_eligibility` | 记录出现在 `records.json` | 出现在 `records_blockers.json` |
|---|---|---|---|---|---|
| **A 候选** | `generated` | `traceable` | `blocked`（当前因 B1/B2/B3/B8 等全局项） | ✅ | ✅（记录全局阻塞） |
| **B 候选·待补证** | `generated` | `missing_original` | `blocked` | ✅（备注含 `待补证`） | ✅（B9） |
| **C 留待确认** | `not_generated` | `unclear_source`（或按具体原因） | `blocked` | ❌ **不得出现** | ✅（原因 + 影响条数 + 解除条件） |

> 三条硬规则：① `not_generated` 的记录**一条都不许**进 `records.json`（C3/C14 断言）；② `missing_original` 的记录可以生成但备注必须含「待补证」（C6）；③ 任何记录都不得出现 `csv_eligible` 之类的乐观值。

### 4.3 资格断言与四态分离（2026-10-23 审计后新增）

**四态必须分别处理，不得互相推导**：

| 态 | 字段 | 取值 | 谁能改 |
|---|---|---|---|
| 生成状态 | `generation_status` | `generated` / `not_generated` | 生成器（纯函数） |
| 证据状态 | `evidence_status` | `traceable` / `missing_original` / `unclear_source` | 生成器 |
| CSV 资格 | `import_eligibility` | `blocked` / `candidate_only` | 生成器（由阻塞表决定） |
| **ID 分配状态** | `id_status`（**派生，新增**） | `assigned_from_map` / `assigned_new` / `unassigned` | 生成器（读 §5.6.5 的 map） |

**断言（C17–C20）**

- **C17**：`import_eligibility` 枚举**只有** `blocked` / `candidate_only`；出现 `csv_eligible` / `ready` / `importable` / `true` 等任何乐观值 → 失败。
- **C18**：`id_status === 'unassigned'` ⇔ `id === null`；且 `id === null` ⇒ `import_eligibility === 'blocked'`（与 §5.6.4 四条硬约束一致）。
- **C19**：**当前阶段 `candidate_only` 预期条数 = 0**。564 条里 A/B 档 502 条全部因全局阻塞（B1/B2/B3/B8）为 `blocked`，C 档 62 条 `not_generated`。生成器必须实时统计，**> 0 时报 `E11_UNEXPECTED_ELIGIBLE` 并整体失败**——放行必须来自一次显式的阻塞解除裁决，不能由代码自行放宽。

> 分配候选档口 ID **不等于**解除任何阻塞：3F 仍缺导览牌与门头照（`TRANSCRIPTION_3F.md` 首节证据边界表），`W03`/`W04` 仍按 D-6 保持 C 档，`stallId` 有值也**不产生**菜品记录，也**不进 CSV**。

#### 5.6.4 `null` 的合法例外（回应审计 C：必填标记与例外规则冲突）

§5.1 把 `id` / `stallId` 标为「必填」，但本轮确有 107 条记录不能分配 `dishId`。**以下为例外条款，与 §5.1 同时生效**，实现者不得因「必填」而拒绝生成，也不得为凑必填而编造 ID。

| 字段 | 何时可以为 `null` | 依据 | 强制联动 |
|---|---|---|---|
| `stallId` | **仅** `W2-04 黄焖鸡店（暂定）` 107 条、`W2-05 炒粉炒面炒饼（暂定）` 27 条——即**名册上无对应项**的档口 | §5.6.1 第 3 条；`TRANSCRIPTION_2F.md:35-36`（两处「名册上找不到对应项」） | `import_eligibility` 恒 `blocked`；`id` 恒 `null` |
| `id` | **仅**「无 `stallId` 的记录」——当前即 `W2-04` 的 107 条（36+32 A + 39 B） | §5.6.2「无 `stallId` 的记录不占号」；`:296` | `import_eligibility` 恒 `blocked`；仍须出现在 `records.json`（A/B 档），**不得**出现在任何 CSV |

四条硬约束（C18 断言）：

1. `stallId === null` ⇒ `id === null`（**不得**出现「有 `stallId` 却无 `id`」以外的反向组合被误用）。
2. `id === null` ⇒ `import_eligibility === 'blocked'`。
3. `stallId === null` ⇒ `import_eligibility === 'blocked'`（即使其它阻塞全部解除也不得放行）。
4. **`id` 非空 ≠ 可导入**：当前 395 条有正式 `dishId` 的记录**全部**仍是 `blocked`（全局 B1/B2/B3/B8 未解除）。

> 反例（明确否定）：把 `id` 非空当作「可导出 CSV」的信号，或把 `id: null` 当作「跳过该记录」的理由——两者都会导致 107 条记录被静默丢弃或被误放行。

#### 5.6.5 稳定 ID 映射策略（已细化：身份域 / 键规范化 / map 结构 / 九类情形）

##### 5.6.5.1 身份域与可变域（回答 A-1 / A-2 / A-5）

| 归属 | 字段 | 理由 |
|---|---|---|
| **身份域**（进键） | `stallId`、`groupKey`（该行菜名**原文**）、`specLabel`（规格/做法/基底，来自表头）、`disambiguator`（仅冲突时人工给） | 这四者描述「这是档口上的哪一道商品」；不随后续观察变化 |
| **可变域**（不进键） | `price`、`tastes`、`foodType`、`name`（由 `groupKey + specLabel` 派生）、`source.detail`（照片序号文本）、`evidence_status`、`note`、`verifyStatus`、`verifiedAt`、`tier`、`generation_status`、`import_eligibility`、`sourceLine`、数组下标 | 都是「观察结果」或「派生展示」，会随补拍、调价、规则迭代而变 |

- **`price` 变化**：键命中且该键在 map 中**唯一** → **复用原 ID**（`id_status='assigned_from_map'`，`gen.note` 记 `price 12→13`）；若该键在 map 中**不唯一**（历史上就存在多条同键）→ **阻塞**，不复用、不新建。
- **`name` 变化**：`name` 是派生字段，不作为新记录判据；若 `groupKey` 本身变了（牌面换了菜名），视为**新键**（见 5.6.5.6 情形①）。
- **`foodType`/`tastes` 变化**：属性更新，复用原 ID；但若与枚举/规则冲突则按 §六 失败，**不得**因「复用」而放过。
- **禁止用作身份**：`sourceLine`（物理行号，任何编辑都会移位——本契约自身从 424 行改到 664 行即为反证）、当前 `price`、数组下标/输出顺序。三者只能作诊断。

##### 5.6.5.2 键的来源与规范化（回答 A-4）

键字符串格式：`<stallId>|<groupKey>|<specLabel>|<disambiguator>`（`id-map.json` 内使用同一格式）。

| 成分 | 来源（**只从这些地方取**） | 规范化规则（必须确定性、可复现） |
|---|---|---|
| `stallId` | §5.6.1 冻结映射；无名册对应项时为 `''`（并强制 blocked） | 原样，不做大小写变换 |
| `groupKey` | 转述稿菜品表的**第一列原文**（拆分前的整格；S1 即菜名，S3/S4 即「口味（现场原文）」那一格） | `trim` → NFKC（全角转半角）→ 内部连续空白折叠为单个空格 → 去掉首尾的 `。，,、；;` ；**不做同义词归并、不删「（素）」之类括注、不改字**。原始串另存 `rawGroupKey` 供审计 |
| `specLabel` | **表头**：S2 的「小碗/大碗」「小份/大份」、S3 的「炒饼/炒面/炒饭」、S4 的「米线/牛筋面/土豆粉」「砂锅米线/牛筋面/土豆粉」、R2 阶梯价的「1 个/2 个/3 个」；S1 无拆分 → `''` | 取表头原文，仅做 5.6.5.2 同款 `trim + NFKC`；**不得**自行改写为「标准名」 |
| `disambiguator` | **仅**来自人工审批记录（牌面照片能区分「哪张牌」，或档主口述系列名） | 形如 `牌-1` / `牌-2` 或 `系列-<牌面原文>`；空值为 `''`。**生成器不得自动生成、不得用价格/行号填充** |

> 之所以不把 `price` 塞进键：价格是**未来会变**的观察值；塞进键会让每次调价都变成「新记录」。之所以不把 `name` 塞进键：`name` 由 `groupKey + specLabel` 派生，重复计入会掩盖 `groupKey` 才是牌面事实这一点。

**`rawGroupKey` 永久保留（B，已冻结 2026-10-23）**：规范化只用于**计算键**；`gen.rawGroupKey` 必须原样保存牌面原文（含全角字符、括注、多空格、异体字）。四条禁令：①不得做同义词归并（「红烧肉」不得并入「秘制红烧肉」）；②不得删除具潜在语义的括注（如「（素）」「（荤）」「（10 个）」）；③不得以价格或输入行号作为身份；④不得在规范化后丢弃原始证据（原文、照片序号、章节位置都必须保留）。

##### 5.6.5.3 为什么必须持久化映射（回答 A-3 的前提）

**结论一：`(stallId, sourceLine)` 不足以作为稳定键。** `sourceLine` 是**物理行号**，任何编辑都会移位——本轮契约自身从 424 行改到 567 行即为反证；两份转述稿在近几轮也多次增删行。故 `sourceLine` 只能作**诊断信息**（命不中时报警），**不得**参与编号决策。

**结论二：纯语义键也不足以唯一化。** 候选键 `K1 = (stallId, name, specLabel)` 在同名同规格不同价时会碰撞，实测至少有：

| 碰撞点 | 具体记录 | 依据 |
|---|---|---|
| 2F `W2-03` | 秘制红烧肉 15 / 16；红烧鸡翅根 13 / 12；黑椒鸡排 14 / 13（3 组真价格差） | `docs/RECORD_AUDIT_PRECHECK_20261023.md:89` |
| 3F | 烤肠 2（W06）vs 1.5（W07 卤味）——**跨档口，本就不构成碰撞**（`stallId` 不同） | `docs/RECORD_AUDIT_PRECHECK_20261023.md:90` + 本轮复核（见 §5.6.5.9.1 C-1/C-2） |

**结论三：本契约采用「语义键 + 持久化映射」双层方案（`id-map.json`）**，因为**源文件里不存在能同时满足「抗重排 + 抗调价」的业务主键**——如实记录，不用猜测补齐。

##### 5.6.5.4 碰撞、消歧与阻塞（回答 A-3）

碰撞的**唯一合法解除方式**是人工给出 `disambiguator`（或修正 `groupKey`/`specLabel` 的抄录错误）。在拿到证据前，**一律阻塞，不猜**：

| 碰撞类型 | 当前实例 | 处理 |
|---|---|---|
| 同一档口下**同名同规格、价格不同**，且无消歧证据 | `W2-03` 三组：秘制红烧肉 15/16、红烧鸡翅根 13/12、黑椒鸡排 14/13 | 该 `K2` 打进 `AMBIGUOUS_KEY` 阻塞：**不分配 ID**、`id_status='unassigned'`、`import_eligibility='blocked'`；要求人工指定「哪张牌为准」或给出 `牌-1/牌-2`。**禁止**用价格大小、出现顺序、行号自动区分 |
| 跨档口同价/不同价同名 | 3F 烤肠 2（`W06`）vs 1.5（`W07` 卤味） | 不算碰撞——`stallId` 不同，键天然不同 |
| 同档口同系列不同名 | **当前无此类实例**（早期以为 `W07` 有两处酸菜肉丝面，复核后属跨档口，见 §5.6.5.9.1 C-1） | 若将来出现，仅当**表头原文**给出系列名（如「汤面/拌面」）时可用 `specLabel` 区分；**取不到就按同名同规格阻塞**，不得凭「看起来像两个系列」自行加 `系列-*` |

> 三条禁令（写进契约，防止「为了让测试变绿」而扩权）：① 不得虚构菜单系列、商品属性或照片对应关系；② 不得用「同价即同物」或「不同价即不同物」反推身份；③ 不得通过删除孤儿映射、重排映射文件或改写键来解决冲突。

##### 5.6.5.5 `id-map.json` 的结构与确定性（回答 B）

文件路径：`tools/pilot/id-map.json`（**本轮不创建**）。结构示例（字段定义见表后）：

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-10-23T15:30:00.000Z",
  "keyFormat": "stallId|groupKey|specLabel|disambiguator",
  "entries": [
    {
      "key": "c01_t07|见面就好|''|''",
      "stallId": "c01_t07",
      "groupKey": "见面就好",
      "specLabel": "",
      "disambiguator": "",
      "dishId": "c01_d040",
      "status": "active",
      "assignedAt": "2026-10-23T15:30:00.000Z",
      "approvedBy": "user",
      "sourceRef": "TRANSCRIPTION_2F.md#W2-01 首行"
    }
  ],
  "orphans": [
    {
      "key": "c01_t20|手抓饼|''|''",
      "dishId": null,
      "status": "orphan",
      "reason": "当前输入中未出现该键（C 档不生成）",
      "lastSeenAt": "2026-10-23T15:30:00.000Z"
    }
  ]
}
```

| 字段 | 含义 | 规则 |
|---|---|---|
| `schemaVersion` | 结构版本 | 整数；不匹配时**失败**（`E15_BAD_MAP`），不做自动迁移 |
| `keyFormat` | 键格式声明 | 固定字符串；不匹配即失败 |
| `entries[].key` | 稳定键 `K2` | **唯一**；重复键 → `E14_DUP_KEY` |
| `entries[].dishId` | 已分配候选 ID | **唯一**；重复 → `E13_DUP_ID`；必须落在 §5.6.2 的连续区间内 |
| `entries[].status` | `active` / `pending_review` | `pending_review` 表示人工已建档但尚未批准分配 ID → 仍不给 ID |
| `entries[].approvedBy` | 批准来源 | 只接受 `user` / `user:牌面照片` 等人工来源；**不得**出现 `auto` |
| `entries[].sourceRef` | 来源追踪 | 指向转述稿章节/照片序号，便于回查；可与 `sourceLine` 并用，但**不参与身份判断** |
| `orphans[]` | 孤儿映射 | **只追加、不删除**；重建 ID 时不得复用其 `dishId` |

**关于 `generatedAt` 与可重复性（必须区分两种确定性）**

- **语义确定性**：同一输入 + 同一 map ⇒ 每条记录的 `dishId`、`key`、`id_status` 完全相同；与 `generatedAt`、条目顺序、文件字节无关。**这是被断言的确定性**（测试侧参考实现 T28/T29）。
- **文件字节确定性**：仅当**剔除 `generatedAt` 与 `orphans[].lastSeenAt` 后**，同时把 `entries` 按 `key` 字典序排序，才可能做到逐字节相同。
- 因此：`generatedAt` **允许存在但不参与身份判断**；任何「字节级相同」的断言必须先做上述剔除与排序，否则不得声称「字节可重复」。

##### 5.6.5.5.1 规范化比较视图（C：已冻结 2026-10-23）

`orphans[].lastSeenAt` 与 `generatedAt`、`entries[].assignedAt`、`publishedAt` 一样**只作审计**：不参与身份键、不参与 ID 分配、不参与语义一致性比较；**不得**用时间戳变化判定记录身份变化。

比较两次运行是否「一致」，只能比较**规范化视图**：

1. 剔除全部时间字段（`generatedAt`、`orphans[].lastSeenAt`、`entries[].assignedAt`、`publishedAt`）；
2. `entries` 与 `orphans` 各自按 `key` 的**字典序**（UTF-16 code unit 升序）排序；
3. 字段按固定顺序输出，缺失值以显式空值占位（不省略键）；
4. 视图再序列化（2 空格缩进 + 结尾换行）后比对。

**表述纪律**：只有在该视图下相同，才可称「语义一致」或「规范化视图字节相同」；**不得**表述为「原始 JSON 文件字节完全一致」——原始文件含时间字段，天然不同。

##### 5.6.5.6 九类情形的自动 / 阻塞 / 人工边界（回答 C）

| 情形 | 自动处理 | 阻塞诊断 | 人工审批 | 结论 |
|---|---|---|---|---|
| ① 首次遇到新键 | 算出键、检查唯一性 | 未命中 map → 不分配 ID | **必须**批准后才写入 `entries` | `id_status='unassigned'`、blocked |
| ② 已存在的键再次出现 | 复用 map 的 `dishId` | 无 | 不需要 | `assigned_from_map` |
| ③ 已存在的键属性变化（价格/口味/类型/照片） | 复用原 ID，`gen.note` 记变化 | 属性与规则冲突时按 §六 失败 | 仅在「变化幅度需确认」时 | 复用，不新建 |
| ④ 输入行序变化 | 键集合不变 ⇒ ID 不变 | 无 | 不需要 | 抗重排成立 |
| ⑤ 记录暂时消失（C 档/未拍） | 该键本轮不出现 | 迁移进 `orphans`（诊断码 `ORPHAN_IN_MAP`，**仅诊断、不阻断**），**不删** | 不需要 | 不占号、不复用 |
| ⑥ 一个旧键对应多条当前记录 | **不自动拆分** | `KEY_COLLISION`（同键多条） | 必须给 `disambiguator` 或修正抄录 | 全部 blocked |
| ⑦ 多个旧键无法区分地对应同一条当前记录 | **不自动合并** | `MERGE_AMBIGUOUS` | 必须裁决保留哪个键，另一个转 `orphans` | 全部 blocked |
| ⑧ 缺少映射文件 | **拒绝开始编号** | `E12_NO_ID_MAP`（整体失败，不写文件） | 需先批准建档 | 不生成 |
| ⑨ map 格式错误 / 重复 ID / 重复键 / `schemaVersion` 不符 | **拒绝加载** | `E15_BAD_MAP` / `E13_DUP_ID` / `E14_DUP_KEY` | 修文件后重跑 | 不生成 |

三条红线：**未命中键不得静默获得 ID**；**孤儿不得删除**；**冲突不得靠重排/改键解决**。

##### 5.6.5.7 实现前置条件

##### A3 审批必须绑定具体计划

- 执行前必须先生成**独立的初始化计划**（只读产出，见 §5.6.5.8 九项内容）。
- 计划至少包含：初始化目的与范围、目标文件路径、初始映射结构、ID 规则、现有映射保护、冲突与证据阻塞处理、完整性与唯一性校验、失败处理、预期文件变化与验收标准。
- 审批记录必须绑定该计划的摘要 `planDigest`（sha256 小写 hex）；`id-map.json` 的 `initialization.planDigest` 必须与之相同。
- **`planDigest` 不匹配 → fail-closed（2026-10-24：D-3 / Q8 情形 A / G-3）**：审批记录所绑定的计划摘要与当前要求不一致时（例如 `initialization.planDigest` 与记录中的 `planDigest` 不同，或计划已实质变更），**必须拒绝**继续初始化或加载；**不得**「警告后继续」，**不得**按旧批准放行。诊断码为 **`E25_PLAN_DIGEST_MISMATCH`**、退出码为 **`1`**（2026-10-24 第二批 G-3；§7.4 登记）。
- **计划发生实质变化 → 原批准不得沿用**，必须重新提交计划并重新取得负责人批准。
- 审批必须明确表达「同意该具体计划 + 仅初始化范围」。**一般性表述不构成批准**：`继续`、`检查一下`、`按你的想法来`、`可以` 等，**不得**自动解释为初始化批准。

- 沿用 §5.6.5.8.1 的旁路记录：路径 `tools/pilot/approvals/<approvalId>.json`、编号 `ap-YYYYMMDD-NN`、批准人标识 `项目负责人`。

### 7.1 失败模式（全部为「整体失败、不写任何文件」）

### 7.2 P1 写出协议（**已批准：用户裁决 D2**）

#### 7.2.1 十个阶段（S1–S10，顺序固定，任何一步失败即止，不得跳步）

| 阶段 | 动作 | 失败处理 |
|---|---|---|
| S1 临时生成 | 在受控临时目录 `gen-<pid>-<ts>/` 内生成**全部**预期输出（`records.json`、`records_blockers.json`、`gen-manifest.json`） | 清理临时目录，退出码 3，打印路径与原因 |
| S2 结构校验 | 校验 JSON 可解析、`schemaVersion`、`records.length`、`entries.length`、`key` 唯一、`dishId` 唯一 | 不进入发布，退出码 1（校验类）/ 3（IO 类） |
| S3 统计对账 | 六项对账：① `meta.counts.A+B+C = meta.counts.total`；② `manifest.counts.records = records.length`；③ `manifest.counts.blockers = entries.length`；④ `manifest.counts.A/B/C = meta.counts.A/B/C`；⑤ 与方案基准 `419/145/564` 一致；⑥ `E9`／`E23` 判据成立 | 失败，打印三元账与两处 counts，退出码 `1`（校验类）／`3`（IO 类） |
| S4 映射一致性 | 校验每条 `id_status` 与 `dishId` 的空/非空一致、`id=null ⇒ blocked` | 同上（继承 S2：校验类 `1`／IO 类 `3`） |
| S5 阻塞状态 | 校验 B/C 档未混入 `records.json`、`candidate_only` 计数为 0 或按 C19 报 `E11` | 失败（退出码 **`1`**），不发布 |
| S6 发布前目标检查 | 目标 `outDir` **必须不存在**；已存在（含空目录）即失败 | 退出码 3，**不覆盖、不合并** |
| S7 单次 rename | 用 `fs.renameSync(tmp, outDir)` 做**目录级**切换 | `EXDEV` → 失败退出（见 7.2.4）；`EPERM`/`ENOTEMPTY` → 失败退出；退出码 **`3`**（IO 类） |
| S8 发布后自检 | 读回 outDir 三个文件；比对 manifest 的 `sha256`（按 §7.2.8 字节口径）与条数 | 失败则报「发布后自检不通过」，退出码 **`4`**，不得声称成功，**且不得继续执行 S9** |
| S9 清除标记 | 删除目标目录内的零字节标记 `PUBLISHING`（**Q6-1=A：只在 S8 通过之后执行**） | 失败即整体失败（`E18_MARKER_CLEAR_FAILED`，退出码 **`4`**），目标目录保留，不得打印成功文案 |
| S10 清除后复核 | **发布后完整性复核（五项，全部纳入）**：① 目录内**不含** `PUBLISHING`（Q6-3=A）；② `records.json`、`records_blockers.json`、`gen-manifest.json` **均存在且可读取**；③ manifest 字段集合**严格等于** `schemaVersion`、`counts`、`recordsSha256`、`blockersSha256`、`publishedAt` 五项且类型合规（§7.2.2 第 6 条）；④ 按 §7.2.8 口径重算两个数据文件的 SHA-256 并与 manifest 比对；⑤ 解析 manifest 的 `counts`，与 `records.length`、`entries.length`、`meta.counts.A/B/C` 逐项对账（§7.2.8） | 失败即**整体失败**，目标目录保留，不得打印成功文案，退出码 **`4`**；诊断码：①`E19`／②`E20`／③`E21`／④`E22`／⑤`E23`（§7.4） |

> **S10 本轮只冻结 ①–③（E2-6）**。④「重算 `records.json`／`records_blockers.json` 的 SHA-256 并与 `gen-manifest.json` 的对应值比对」与 ⑤「按契约解析两个数据文件、核对记录数量与 `counts` 一致」**暂不纳入 S10**：现有契约**没有唯一确定**哈希的计算对象与编码（是否含结尾换行、是否规范化 JSON），也**没有唯一确定** `gen-manifest.json` 的 `counts` 结构与「记录数量」口径（§3.3 的 `counts` 是 `records.json` 的 `meta` 示例，不是 manifest 定义；`records_blockers.json` 连字段结构都未定义）。两项分别登记为待决 `Q-HASH`、`Q-COUNTS`（§10.6.2），负责人指定前**不得**写入 S10、不得由实现自行假定口径。

#### 7.2.2 保证与不保证（**必须逐字区分，不得混写**）

**保证**：

1. **单次目录 rename 在文件系统层面是原子的**：观察者只可能看到「目标目录不存在」或「目标目录内三个文件齐全」两种状态（同卷前提下）。
   **适用范围（E2-5）**：本条只描述 S7 那一次 `rename` 调用带来的可见性，**不包含** S9 对 `PUBLISHING` 标记的清除过程。S8 之后、S9／S10 完成之前，目标目录处于「三个文件齐全、且可能仍含 `PUBLISHING`」的状态；**S8→S10 整体不是原子事务**，契约不在该范围内提供原子性保证。
2. 任一前置校验（S2–S5）不通过时，**目标路径不会被创建**。
3. 目标已存在时**一律失败**，不覆盖、不合并、不静默替换。
4. 失败时保留诊断信息（临时目录路径、失败阶段、错误码、已生成文件清单）。
5. 跨卷（`EXDEV`）**不得退化为逐文件拷贝**：直接失败。
6. 每次运行都会在 `gen-manifest.json` 写入 `schemaVersion`、`counts`、`recordsSha256`、`blockersSha256`、`publishedAt`，供读侧与下一次运行识别。**字段集合恰好为这 5 个**（Q6-5=C 严格档）：读取方遇到**任何额外字段一律判错**（等价 `additionalProperties = false`）；新增字段属**破坏性变更**，必须同时修改本条与 `tools/test_records_spec.js`。
7. **只有「S8 通过 → S9 清除成功 → S10 复核通过」三者齐备，才可宣告发布成功**（Q6-1=A / Q6-2=A / Q6-3=A）；任一环节失败均为整体失败，且不得打印任何成功文案。**在 S10 复核成功之前，不得打印任何发布成功文案，也不得对外宣告发布成功**（E2-3）；S8、S9、S10 任一步失败时，均不得出现成功宣告。

8. **`counts` 的结构与对账（C-2=A）**：`gen-manifest.json.counts` 恰为 `{records, blockers, A, B, C}` 五个整数字段；`records` = `records.json` 实际条数，`blockers` = `records_blockers.json.entries.length`，`A/B/C` 为分层候选数。**`manifest.counts.A/B/C` 必须等于 `records.meta.counts.A/B/C`**；**不新增 `counts.blocked` 字段**（`blocked` 仅作运行时统计）。字段类型与失败判据见 §7.2.8。

**不保证（写进契约，防止后人误信）**：

1. **不保证多文件整体事务原子性**——三个文件不经过独立事务提交；它们只是恰好同处一个目录，靠一次 rename 一起出现。「连续三次单文件 rename」在任何情况下都**不得**被描述为整体原子提交。
2. **P1 是唯一允许的正式写出策略**（用户裁决 D2 收尾 §D）。契约中不存在 P2（单文件顺序写）或 P3（单文件合并）作为可选项；任何实现都不得切换到按文件顺序发布、复制发布或覆盖写出。若某项保证在当前环境无法满足，正确做法是**报告并停止**，而不是降级。
3. 不保证**断电/进程被 kill 期间**的不可见中间态：rename 前崩溃 → 临时目录残留；rename 后崩溃 → 目标齐全，但发布标记可能尚未落盘（见 7.2.3）。
4. 不保证同一路径**并发两次运行**的安全性：并发检测靠目标不存在这一前提，第二次运行会因 `outDir` 已存在而失败——这是**拒绝**而非排队。
5. 不保证 `outDir` 所在卷的 `fsync` 语义（Node 对目录 fsync 的支持随平台而异），故不承诺「崩溃后一定可见」。

#### 7.2.3 发布标记与「上一次发布不完整」的识别

- 临时目录内先写 `gen-manifest.json`，**最后**引入一个零字节标记 `PUBLISHING`（同目录），随后才执行 S7 的目录 rename。标记随目录一起被搬走，故目标目录若出现 `PUBLISHING`，说明「rename 完成但收尾未完成」。
- **清除动作（Q6-1=A）**：**S8 通过之后**，由生成器删除目标目录内的 `PUBLISHING`；删除失败按**整体失败**处理（Q6-2=A），目标目录保留，不得打印成功文案；清除完成后必须执行 S10 复核（见 §7.2.1）。
- 读侧规则：目标目录存在但**缺** `gen-manifest.json` 或含 `PUBLISHING` → 判定为**不完整发布**，报 `E17_INCOMPLETE_PUBLISH`，拒绝作为输入使用。
- 读侧**不增加**来源或批次校验（**Q6-6=A**）：除上一条列明的两种拒绝条件外，契约不要求读取方核验目录的来源、批次号或创建时间。「完整但非本次运行产生」的目录按上一条判定即可被接受，这是**有意接受的边界**，不是遗漏。
- **S9→S10 的读侧窗口（E2-4：现有协议行为，不是新机制）**：S9 删除 `PUBLISHING` 之后、S10 复核完成之前，读侧**可能**已按上一条规则接受该目录。读侧当前**只**按「缺 `gen-manifest.json`」与「含 `PUBLISHING`」两个条件拒绝，**不新增**等待、锁、额外文件或任何其他检查。读侧接受该目录**不等于**生成器已完成 S10，也**不等于**生成器已打印成功消息。
- 修复路径（**Q6-7=D**）：**按失败类型分列**，见 §7.2.7。本节不再使用「只能是人工移除该目录」这类排他表述；生成器**不得自动删除**任何目录或标记。
- 这是**弱协议**：它让不完整可被识别，但**不提供**回滚能力。

#### 7.2.4 跨卷与 `EXDEV`

- 临时目录默认建在**目标卷**（`path.dirname(outDir)` 同级）；若无法建在同卷，先探测 `path.parse(tmp).root === path.parse(outDir).root`，不同则调用前直接失败，**不进入** S1。
- 一旦 `rename` 抛 `EXDEV`，只允许报告并退出；**禁止**「先复制再删源」的降级路径（上一轮已实测：`Move-Item` 在目标非空时会静默合并，属不可接受的破坏行为）。

#### 7.2.5 诊断保留与清理

- S1–S5 失败：删除临时目录，但**先把**其路径、阶段、错误码、部分产物清单打印到 stderr；退出码 1/3。
- S6 失败：临时目录**保留**（不删），以便人工查看，打印路径 + 提示「目标已存在，手工确认后再重跑」。
- S7 失败（**情形一·外部并发创建**）：临时目录保留；若目标目录已被**外部**创建且不完整，按 7.2.3 报 `E17`。
- S7 失败（**情形二·`rename` 本身失败**）：临时目录保留；目标路径的实际状态**按本次运行的实际结果报告**——不得无条件声称「目标一定不存在」，也不得假定「目标一定由本次运行创建」；若目标存在，按 7.2.3 判定其完整性。此判断依赖文件系统 `rename` 语义，属**运行时事实**，契约不将其上升为文件系统无关的保证。
- S8 失败：**不删**目标目录，报失败；诊断中写明「目录已存在但自检未通过」，且不得打印任何成功文案。
- **S9 清除失败**：目标目录**保留**（不删），报 `E18_MARKER_CLEAR_FAILED`，打印目录路径与该错误码，**不得**打印任何成功文案。
- **S10 复核失败**：目标目录**保留**（不删），打印目录路径与**逐项结果**（① 标记是否存在／② 三文件是否可读／③ manifest 字段集合与类型是否合规／④ 两个哈希是否一致／⑤ 条数与分层数是否一致）。①→`E19_MARKER_STILL_PRESENT`、②→`E20_S10_FILE_UNREADABLE`、③→`E21_S10_MANIFEST_INVALID`、④→`E22_S10_HASH_MISMATCH`、⑤→`E23_S10_COUNT_MISMATCH`（§7.4）；退出码 **4**。**不得**打印任何成功文案。
- **S10 失败一律禁止**（E2-6）：不自动删除目录、不重建产物、不修改 `gen-manifest.json` 或任何数据文件来「凑过」检查、不降级为逐文件复制或顺序写。修复路径见 §7.2.7（人工移除整个目录后重跑），**不构成事务回滚**。

#### 7.2.7 修复路径（按失败类型，**Q6-7=D**）

#### 7.2.8 哈希与计数口径（**已裁决 2026-10-24：H-1 / H-2 / C-2 / C-3**）

**哈希（H-1=A，八条）**：

1. 计算对象是文件**实际写入的完整字节**：不重序列化、不重排键、不做空白规范化。
2. 文件编码为 **UTF-8，不带 BOM**。
3. **不对换行符做任何转换**；按实际写出的字节计算，**保留文件实际存在的末尾换行**。
4. 结果为 SHA-256 的**小写十六进制、64 字符**。
5. **S8 在写入 `gen-manifest.json` 之前**，对 `records.json` 与 `records_blockers.json` 的最终字节各算一次哈希，写入 `recordsSha256`、`blockersSha256`。
6. **S10 重新读取这两个文件**，按同一口径重算并与 manifest 中的两个哈希比对。
7. `gen-manifest.json` **自身不参与自我哈希**（它只是这两个哈希的载体）。
8. 哈希不匹配**必须导致整体失败**；**不得**自动重写、修复或覆盖任何数据文件。

**读侧（H-2=A）**：读侧**不新增**哈希校验。§7.2.3 的两条拒绝条件、`E17_INCOMPLETE_PUBLISH` 的语义与 `T66` 的口径**均保持不变**；哈希校验只发生在生成器侧的 S10。新增读侧校验会改变已冻结的 `Q6-6=A` 边界，**本轮明确不做**。

**`gen-manifest.json.counts` 结构（C-2=A）**：

| 字段 | 类型 | 含义 |
|---|---|---|
| `records` | 整数 | `records.json` 的**实际记录数**（`records.length`）；当前规划基准 **502** |
| `blockers` | 整数 | `records_blockers.json` 的 `entries.length`，按**待阻塞记录**计数，不是「记录 × 原因」对数 |
| `A` / `B` / `C` | 整数 | 分层候选数；当前规划基准 **463 / 39 / 62**。C 档不进 `records.json`，但仍计入分层统计 |

- **两处必须相等**：`manifest.counts.A/B/C` **必须等于** `records.meta.counts.A/B/C`；两者**不是**互相独立的真源。
- **不新增 `counts.blocked`**：`blocked`（`import_eligibility === "blocked"` 的正式记录数，当前规划基准 502）只作为**运行时统计量**打印与对账，**不得**写进 manifest（§7.2.2 第 6 条把字段集合限定为 5 个）。若将来证明确有必需对账无法完成，须先提交负责人复核，不得自行加字段。
- **规划基准 ≠ 运行时实测**：564（规划候选总数）／502（正式记录数）／463·39·62（分层候选）／0（可入 CSV）均只是**当前规划基准**；运行时必须按实际数据计算，**不得硬编码**。实际值与基准不符时按 S3 失败，**不得**自动修正或静默放行。
- **计数语义（C-3=A）**：`records.meta.counts.total = 564` 表示规划候选总数，**不表示** `records.length`；`A/B/C` 为分层候选数；`blocked` 为被阻塞的正式记录数；`blockers` 为待阻塞记录条数。四者互不等价、互不推算。

### 3.5 CLI 调用与参数检查顺序（**已裁决 2026-10-24，第二批；G-1=A**）

> **性质**：本节规定的是**契约要求的检查顺序**，不是对现有实现的描述。截至本裁决执行时，生成器 `tools/pilot/gen_records.js` **尚未实现**（见 §十一），因此「运行时是否按此顺序报错」**尚未验证**，只能由实现落地后的集成测试（`T100`，当前 PENDING）证明。

检查顺序（自上而下，命中即停）：

| 序 | 检查项 | 失败时 | 退出码 |
|---|---|---|---|
| 1 | 子命令／命令名是否被契约承认 | `E27_CLI_USAGE` | `2` |

**通用规则**：

1. **遇错即停**：任一步发现错误，立即报告**该步的首个错误**并停止，**不继续检查后续步骤**。
2. **不聚合多错**：一次运行**只报一个** CLI 错误，不输出多错清单、不合并错误码。
3. 同一检查步内若有多个同类错误（例如两个未知选项），按**命令行从左到右**的书写顺序取**首个**；不得另行规定未经授权的优先级。
4. `write = true` 且**未提供** `--out` → `E24_MISSING_OUT`，退出码 `2`（§3.2）。它发生在第 3 步，但语义独立、**不**归入 `E27`。
5. **输出路径安全检查**（§7.2.6）发生在 CLI 语法检查**全部通过之后**；被拒绝时 `E28_OUT_REFUSED`，退出码 `3`。
6. 通过前置检查后发生**实际写盘失败** → `E10_WRITE_FAILED`，退出码 `3`（原义不变，**不**扩张到受保护目录或非空目标）。

> **不得**为同一输入同时报两个 CLI 错误；**不得**把 `--out` 相关的**所有**失败一律归为 `E28`（缺参是 `E24`，语法错误是 `E27`）。
> 若出现本节五步无法判定先后的输入形式（例如某参数既可视为值也可视为子命令），**先报告规范缺口**，不得自行设定优先级。

## 八、与 `tools/verify_data.js` 的复用边界

### 8.1 可复用的规则（只调用，不修改）

| 复用项 | 用法 | 注意 |
|---|---|---|
| `AREA_VALUES` / `TASTE_VALUES` / `FOOD_TYPE_VALUES` / `SIDE_VALUES` / `NO_STATUS_VALUES`（`tools/verify_data.js:62-66`） | 生成器从 `data/index.js` 的枚举**间接**取同一来源，断言用同一份 | 不得在生成器里硬编码第二份枚举 |
| `D5`（价格：有限正数 / ≤1 位小数 / >100 警告，`PRICE_MAX`） | 对草稿逐条跑 | 警告不等于失败 |
| `D7`（`tastes` 单值且在枚举内） | 同上 | `choice` 已在枚举内（`data/index.js:44`） |
| `S1/S2/S3`（店铺必填、`id` 唯一） | 对**拟建的** `c01` 店铺/窗口做结构校验时复用 | 见 8.2 的 checkJoin 限制 |
| `checkMeta` 系列（P1–P6） | 复用其对 `source`/`verifyStatus`/`verifiedAt` 的判定语义 | P6 的 `declaredDemo` 语义对新草稿不适用（草稿不是 demo 数据集） |

### 8.2 **不可**直接复用的规则

| 规则 | 为什么不能直接用 | 正确做法 |
|---|---|---|
| `checkJoin`（J1「join 后找不到该菜品」） | 它校验的是**仓库当前数据层** `dataLayer.ALL_DISHES`（`tools/verify_data.js:505` 附近），而草稿尚未导入 `data/` → 单独对新草稿跑必然全红 | 要么 `checkJoin: false`；要么构造「仓库现有 45 条 + 新草稿」的**合并集**再跑 |
| `D8` 自然键去重 | 生成器内部已有 `groupKey`／规格后缀，D8 的自然键（shopId+stallId+name+price）在 `id` 为 `null` 时无法唯一化 | 生成器用自己的 `groupKey+specLabel` 去重；D8 留到导入阶段 |
| `J3/J4`（店铺无窗口/无菜品 → 警告） | 草稿的店铺是「拟建」的，必然短暂无窗口 | 不对草稿跑 J3/J4 |
| `--require-evidence` 严格模式 | 需要真实图片文件存在，当前 `tools/pilot` 下**没有任何 `c01_*` 图片文件**（只有一个空骨架目录 `c01_service_2f/`；现有 5 张实拍全是 `c02_*` / `c03_*`） | 留到 CSV 阶段；本轮生成器只校验 `source_detail` 文本形态（C2/C3） |

### 8.3 建议的衔接方式（不在本轮实现）

1. 生成器自有的 §4.3（`C17`–`C20`）+ §6.2 规则表所列断言先跑（纯函数，不依赖 `verify_data.js`；原「C1–C16」编号体系未定义，见 §10.7）；
2. 再对「合并集」跑一次 `verify_data.validateDataset({ shops: repoShopsPlusC01, dishes: repoDishesPlusDraft }, { checkJoin: true })`，把它返回的 `errors` **全部转成 blockers**（而不是抛错），用于提前暴露结构冲突；
3. 导入阶段仍走现有 `tools/import_data.js`（它已强制 `unverified`/`verifiedAt=null`、拒收 `verify_status` 列、校验证据文件存在）。
