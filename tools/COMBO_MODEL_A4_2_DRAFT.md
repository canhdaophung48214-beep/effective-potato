## 二、关系图

建议采用共享 `dishes` 主体表 + 独立 `comboItems` 组件关联表。

**shops · 店铺** —— 一份套餐只能归属一家店铺。

**stalls · 窗口** —— 每个窗口属于一个店铺，并关联所属楼层。

**dishes · 推荐对象主体**

- 普通单品：`recordType=dish`，有明确窗口，价格为单品价。
- 套餐：`recordType=combo`，`stallId` 可为空，价格为整份总价。

**comboItems · 套餐组件关联** —— 通过 `comboId` 关联套餐主体，通过 `dishId` 关联普通单品。一个套餐包含多个组件；一个单品可以被多个套餐复用。

关键约束：套餐主体的 `shopId` 是套餐归属店铺；每个组件所关联的单品必须属于同一家店铺。组件可以来自不同窗口、不同楼层，但不能跨店铺。

## 三、主体表字段字典：`dishes`

以下是目标模型。现有单品数据保持兼容，新增字段应通过兼容层提供默认值，而不是要求立即重写现有 45 条记录。

| 字段 | 类型 | 单品规则 | 套餐规则 |
| --- | --- | --- | --- |
| `id` | string | 必填，唯一 | 必填，唯一 |
| `recordType` | enum | `dish` | `combo` |
| `name` | string | 单品名称 | 套餐名称 |
| `price` | number | 单品价格 | 整份套餐总价 |
| `shopId` | string | 所属店铺 | 套餐归属店铺 |
| `stallId` | string | 必填，实际窗口 | 可为空；非空时表示主取餐窗口 |
| `foodType` | 现有类型 | 沿用现有语义 | **必填一个代表性类型**（见 Q1） |
| `tastes` | 现有类型 | 沿用现有语义 | **允许为空，不汇总组件口味**（见 Q1） |
| `saleMode` | enum | `solo` 或 `combo_only` | 固定为 `solo` |
| `recommendEligible` | boolean | 是否可独立推荐 | 是否允许独立推荐 |
| `comboComplete` | boolean | 兼容默认 `true` | 只有组件验证完成后才能为 `true` |
| `comboNote` | string | 可空 | 不完整套餐必须填写原因 |

### 字段语义

- `saleMode=solo`：该单品可以单独售卖。
- `saleMode=combo_only`：该单品只能作为套餐组件提供。
- `recommendEligible=true`：允许作为独立推荐对象进入列表和随机池，但仍需满足核验、完整性及筛选条件。
- 套餐主体固定 `saleMode=solo`，避免套餐再被定义为只能包含在其他套餐里的组件。

对于 `combo_only`，还必须至少被一个有效套餐引用；否则作为孤儿记录发出校验警告或错误。实施前应决定这类数据应当报错还是允许暂存。

### 合法组合

| `saleMode` | `recommendEligible` | 结果 |
| --- | --- | --- |
| `solo` | `true` | 可以单独售卖并独立推荐 |
| `solo` | `false` | 可以单独售卖，但不独立推荐 |
| `combo_only` | `false` | 仅作为套餐组件，不独立推荐 |
| `combo_only` | `true` | 非法，校验失败 |

注意：`recommendEligible=true` 并不意味着一定会被推荐。完整性、数据核验状态和用户筛选条件仍然有效。

## 四、套餐组件表字段字典：`comboItems`

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `id` | string | 是 | 关联记录唯一 ID |
| `comboId` | string | 是 | 必须关联 `recordType=combo` 的主体 |
| `dishId` | string | 是 | 必须关联存在的 `recordType=dish` 单品 |
| `quantity` | integer | 是 | 大于等于 1 |
| `optional` | boolean | 是 | 默认 `false` |
| `extraPrice` | number 或 null | 否 | 仅可选组件可设置，非负数，最多一位小数；**`optional=true` 且为空 = 免费可选项（合法）** |
| `collector` | string | 按采集模式 | 沿用现有来源记录规范 |
| `collect_date` | string | 按采集模式 | 沿用现有采集日期规范 |
| `evidence_file` | string | 按采集模式 | 沿用 A2 证据文件校验规则 |

关联规则：

1. 套餐至少包含两个有效组件。
2. 同一个套餐不能重复加入相同单品关联；若确实需要多份，应通过 `quantity` 表达。
3. 必选组件的 `extraPrice` 必须为空。
4. 可选组件允许有额外价格，但套餐总价与可选项加价必须明确区分。
5. 组件必须属于套餐主体对应的店铺，但可以来自不同窗口和楼层。
6. 组件必须是普通单品主体，不能直接把另一个套餐作为组件。

## 五、派生字段字典

这些字段由数据组装层计算，禁止导入者直接填写。

| 字段 | 计算规则 | 用途 |
| --- | --- | --- |
| `stallIds` | 有效组件所属窗口去重 | 窗口筛选 |
| `floorIds` | 有效组件所属楼层去重 | 楼层筛选 |
| `windowCount` | `stallIds.length` | 展示涉及窗口数量 |
| `itemCount` | 有效组件的数量 | 展示「含 N 项」 |
| `componentPriceSum` | 必选组件单价乘数量后求和；可选项单独处理 | 价格异常预警 |
| `hasCrossWindow` | `windowCount > 1` | 跨窗口提示 |
| `comboFingerprint` | 由规范化后的组件关系计算 | 重复套餐识别 |
| `windowRefs` | `[{ stallId, floorId, stallLabel, floorLabel }]`，由组件窗口查店铺表得到 | 卡片/详情渲染「2 楼 2 号窗口、1 楼 1 号窗口」（见 B6） |

需要强调两点：

- `componentPriceSum` 不是套餐售价，不参与预算判断。
- `windowCount` 是有效组件的窗口去重数，不是组件数量；两个组件来自同一个窗口时，`windowCount=1`。

## 六、唯一性规则与套餐指纹

建议区分两个概念：

1. **主体 ID**：套餐记录的稳定标识。套餐改名或改价不应通过新建同名记录来隐式覆盖旧记录。
2. **套餐指纹**：用于识别组件构成完全相同的重复套餐，不取代主体 ID。

推荐的规范化指纹输入包含：

- 套餐归属 `shopId`；
- 组件的 `dishId`；
- 每个组件的 `quantity`；
- 每个组件的 `optional` 状态；
- 可选组件的 `extraPrice`。

将组件按稳定规则排序后计算指纹，避免仅仅因为 CSV 行顺序不同就生成不同指纹。**指纹不包含 `price`**（见 §12 决策 3）。

同店同名同价、但组件不同的套餐可以并存；组件完全相同的套餐应触发重复检查。套餐名称或价格变化属于主体修改，组件集合变化属于套餐内容修改，不能简单地把它们都视为新的套餐 ID。

重要边界：指纹适合重复检测，但是否应当阻止导入，仍需要考虑同一家店确实存在两个不同销售版本的情况。建议默认报告冲突，由人工确认，而不是不加区分地静默跳过。

## 七、筛选、预算与随机推荐

### 窗口与楼层筛选

- 普通单品继续按自身 `stallId` 和 `floorId` 匹配。
- 套餐按 `stallIds`、`floorIds` 判断。
- 命中任一组件窗口或楼层即可展示整份套餐。
- 卡片不删除其他窗口的组件信息。
- 套餐主体 `stallId` 若非空，必须是归属店铺下的有效窗口；它表示主取餐窗口，不代替组件实际窗口清单。

### 预算

预算直接比较主体 `price`：

```
符合预算  ⇔  主体价格 ≤ 预算上限
```

套餐主体 `price` 是整份套餐总价，组件价格不重复相加。价格比例异常（低于 `0.5×` 或高于 `1.2×`）只触发复核提示。

### 随机推荐

- 推荐池以 `dishes` 主体为单位。
- 完整套餐可以作为一个候选对象。
- 不完整套餐不进入随机池。
- `recommendEligible=false` 的单品不进入独立推荐池。
- 组件关系不单独增加套餐权重。
- 组件如果本身允许单独售卖且可独立推荐，可以继续作为普通单品被推荐。

### 统计

- 推荐对象总数包含可展示的单品和套餐。
- 店铺数量仍然按 `shopId` 去重。
- 为避免「共 N 道菜」误导用户，实际页面文案建议改为「共 N 个推荐对象」，或者分别展示「单品 N 道 · 套餐 M 份」。具体页面修改暂不授权。

## 八、套餐卡片与详情展示规范

套餐示意：

```
香辣鸡腿饭套餐                       套餐
¥18
整份价 · 含 2 项 · 涉及 2 个窗口
一号食堂 · 2 楼 2 号窗口、1 楼 1 号窗口
部分菜品可能需要到其他窗口取餐。
```

详情页需要提供：

- 套餐总价和套餐核验状态。
- 所含单品、数量和可选项。
- 每个组件对应的窗口和楼层。
- 跨窗口取餐提示。
- 套餐不完整时的原因说明；不完整套餐不参与随机推荐。

以上是展示规范示例，不代表现有页面已经支持这些内容。

## 九、实施前必须保留的兼容性约束

1. 现有 45 条单品数据不应被要求立即迁移。
2. 历史单品缺少新增字段时，由兼容层注入默认值。
3. 新套餐的 `comboComplete=true` 必须以组件校验通过为前提，不能无条件赋值。
4. 现有单品自然键保持 `shopId + stallId + name + price`；套餐采用独立指纹规则。
5. 首批仍然只采单品，不修改当前导入白名单，不提前导入套餐。
6. 页面、筛选器、验证器和导入器应分别实现并分别测试，不能只在某一层增加套餐字段就视为完成。

## 十一、实施前置条件（源码已核对，2026-10-22）

以下是设计稿与现有代码的硬冲突点。它们不改模型，只要求实施时**必须同时改这些位置**，否则第一批套餐数据进不来、或进得来但显示错。

| 编号 | 冲突 | 源码位置 | 实施时必须做的事 |
| --- | --- | --- | --- |
| **B1** | 现有校验要求 `tastes` 恰好 1 个元素，套餐「不汇总口味」会被直接判错 | `tools/verify_data.js:341-349`：`dish.tastes.length !== 1` → `err('D7', ...)` | D7 增加分支：`recordType === 'combo'` 放行空数组（Q1 已定） |

补充澄清项（不阻断，但必须写清）：

- **C1**：`optional = true` 且 `extraPrice` 为空 → **合法**，表示免费可选项（加辣、加葱）。已并入第四节字段表。
- **C2**：指纹**不含 `price`**；组件构成相同但价格不同 → 报告冲突、人工确认，不静默覆盖。
- **C3**：统计口径 —— `DATA_STATUS_SUMMARY`（`data/index.js:408-411`，经 `countByStatus`）只分状态、不分类型。套餐入库后「共 N 道菜」会失真，需与页面文案改动一起做；首批不涉及（见 §12 决策 2）。
- **C4**：`applySort`（`utils/matcher.js:248-260`）按 `price` 混排套餐与单品，同价并列可能引起误解，靠文案区分，不改排序算法。

## 十二、本轮决策落定（2026-10-22）

| # | 决策点 | 结论 |
| --- | --- | --- |
| 1 | 套餐 `foodType` / `tastes` 语义 | `foodType` **必填一个代表性类型**，确保能被对应类型筛到；`tastes` **允许为空**，不汇总组件口味；`tools/verify_data.js` 的 D7 需为套餐增加放行分支（B1） |

| 4 | 可选项 `extraPrice` 为空 | **合法**，表示免费可选项 |
